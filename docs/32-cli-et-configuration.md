# 32 · CLI & configuration (mjs.config.json)

> 📚 Pas de chapitre de tuto interactif dédié (la ligne de commande et son fichier de configuration vivent hors de l'éditeur live) : cette page se suffit à elle-même. Les encarts 🎓 *Pour débutants* dépliables donnent l'explication pas-à-pas ; le corps de la page reste la référence dense.

Les chapitres précédents documentent le langage MJS côté client — composant, réactivité, événements… Celui-ci documente l'autre moitié, tout aussi nécessaire dès la première minute passée sur un projet : la commande `mjs` et le fichier `mjs.config.json` qui la configure.

## 1. Les commandes

| Commande | Ce qu'elle fait |
|---|---|
| `mjs init` | scaffolde `mjs.config.json` et la structure de départ du projet |
| `mjs build` | compile une fois et sort |
| `mjs dev` | watch + rechargement à chaud qui garde l'état de la page (serveur HTTP+WS sur `--port`, défaut 3939) |
| `mjs check` | vérifie la config, liste les composants détectés et toutes les fautes de chaque fichier en échec (compile réellement, comme `build`) |
| `mjs serve` | sert le rendu SSR/prérendu par requête (`render.routes`) — bloc `render` requis dans `mjs.config.json` (port 3000 par défaut) |
| `mjs ws` | lance le serveur temps réel (MJS-WS) — fichier d'entry `ws.server.mjs`/`ws.js`/`server/ws.js`… |
| `mjs server` | lance le serveur de jeu (MJS-Server, `mjsServer` + `app.game`) — fichier d'entry `game.server.mjs`/`game.js`/`server/game.js`… |
| `mjs mcp` | serveur MCP (stdio) pour les assistants d'IA : la doc de la version installée, la compilation d'un composant, les erreurs de la page — cf. [40 · Travailler avec une IA](40-travailler-avec-une-ia.md) |

### `mjs init`

Scaffolde un projet MJS **autonome** — aucune dépendance à Rails/Sprockets ni à un autre framework, le dossier de sortie est servi tel quel par n'importe quel serveur statique. Elle crée, à la racine du projet, neuf éléments :

- les dossiers `app/modularjs/`, `app/modularjs/styles/`, `app/modularjs/examples/` et `public/modularjs/` ;
- le fichier `mjs.config.json` de départ ;
- le composant d'exemple `app/modularjs/hello.mjs` (un compteur, `<script>` en Civet + `<style lang="scss">`) ;
- `AGENTS.md`, avec le bloc MJS pour les assistants d'IA (la version installée, où lire sa doc — cf. [40 · Travailler avec une IA](40-travailler-avec-une-ia.md)) ;
- dans `app/modularjs/examples/` : `hello-world.mjs` (un composant de référence qui montre les cinq blocs d'un fichier `.mjs` dans l'ordre canonique, et affiche cette liste lui-même) et `README.md` (la convention énoncée en clair).

Le `mjs.config.json` écrit est celui-ci, mot pour mot :

```json
{
  "sourceDir": "app/modularjs",
  "outputDir": "public/modularjs",
  "manifestPath": "public/modularjs/bundle.js",
  "stylesheetsDir": "app/modularjs/styles",
  "lang": "fr",
  "defaultScriptLang": "civet"
}
```

> **Développement ou production ?** C'est la **commande** qui tranche, pas le fichier : `mjs build` construit en développement, `mjs build --prod` en production. `minify` ne fait que minifier : un projet peut vouloir un bundle compact **en développement** sans rien perdre pour autant — le panneau d'inspection, les cartes de source, `µ.debug` et tout ce que la console écrit (`µ.log`, `µinspect`, les avertissements) restent comme sans minification.

`mjs init` n'écrase **jamais** un fichier ou un dossier déjà présent : elle le saute et l'annonce (« ↪️ … (existe déjà) ») plutôt que d'écrire par-dessus. Seul un `AGENTS.md` déjà là change : il reçoit le bloc MJS en fin de fichier, le reste intact à l'octet près. Tant que `modularjs-framework` n'est pas installé dans le projet, `npx --no -- mjs dev` ne lance rien : `--no` empêche npx d'installer à sa place un paquet nommé `mjs`, qui n'est pas ModularJS. C'est npm qui répond, en anglais : « npx canceled due to missing packages and no YES option » quand il joint son registre, une erreur de réseau quand il ne le joint pas (`ECONNREFUSED` sans connexion, `ENOTCACHED` en mode hors ligne). Dans les deux cas, lancez `npm install modularjs-framework` — cette commande-là demande le réseau —, puis relancez la commande. En fin de commande, `mjs init` affiche donc les prochaines étapes telles quelles, l'installation d'abord :

```
Pour démarrer (la première commande installe MJS dans ce projet : une fois suffit) :
  npm install modularjs-framework
  npx --no -- mjs dev
  → http://127.0.0.1:3939

Inclure le HMR client dans votre HTML :
  <script src="http://127.0.0.1:3939/__mjs_hmr/client.js"></script>
  <script type="module" src="/modularjs/bundle.js"></script>
  <mjs-hello></mjs-hello>
```

### `mjs check`

Imprime d'abord les chemins résolus :

```
Source dir   : …
Output dir   : …
Manifest     : …
Stylesheets  : …
Default lang : …
```

puis compile **pour de vrai** — ce n'est **pas** une compilation à blanc : les fichiers sont écrits dans le dossier de sortie, exactement comme `mjs build`, et la commande le rappelle elle-même avant de lancer la compilation (« 'mjs check' compile réellement (comme 'build') — les fichiers … seront écrits/écrasés »). Elle liste ensuite les composants détectés (les 20 premiers, puis un compte des suivants), et sort avec le code **1** à la moindre erreur de compilation, **0** sinon. Le bilan des avertissements (« N avertissement(s) », écrit aussi par `mjs build` et au premier passage de `mjs dev`) s'écrit après la dernière ligne d'avertissement de la compilation ; il compte les avertissements de sa liste et ceux déjà écrits plus haut, et le dit (« 13 avertissement(s), dont 7 écrits plus haut ») : N est le nombre d'entrées `warnings` de `mjs check --json`. Une erreur n'y compte jamais, même étiquetée `[lint.<type>]` (un composant sans HTML sous `"emptyComponent": "error"`) : elle compte parmi les erreurs, et figure dans `errors`.

C'est la porte d'entrée naturelle d'un pipeline d'intégration continue : un `mjs check` qui sort en 1 casse le pipeline sans qu'il soit besoin de lancer le moindre serveur.

**Toutes les fautes de chaque fichier.** `mjs build` et `mjs dev` donnent la première faute de chaque fichier en échec, et leur bilan le rappelle d'une ligne ; `mjs check` les liste toutes, rangées par fichier : le fichier et son nombre de fautes, chaque faute avec sa place (`chemin:ligne:colonne`, quand elle est sûre) et son message, puis le total et le nombre de passes de compilation qu'il a fallu. Dans un composant, `mjs check` relit le fichier autant de fois qu'il le faut, la faute d'avant corrigée comme son message le dit (une minuterie est rendue inerte le temps de la relecture) : chaque faute listée est une faute que la construction donne, une fois corrigées celles qui la précèdent dans la relecture ; la première listée est celle qu'elle donne aujourd'hui, les suivantes sont rangées par ligne, et celle où la lecture s'arrête vient en dernier, avec sa note ; leurs places sont celles du fichier tel qu'il est. Les refus qui portent leur correction : l'ancienne écriture d'un mot de MJS (`@lightDom` pour `:lightDom`, `<style @css>` pour `<style :css>`), une directive `@import` écrite sur plusieurs lignes, avec une virgule entre ses noms ou un import par défaut entre accolades, une minuterie (`setTimeout`, `setInterval`) écrite en clair dans le `<script>`, une expression du gabarit qui finit par un opérateur (`{if $a ==}`). La liste d'un fichier s'arrête, avec la note « la suite du fichier n'est pas lue », sur une faute que MJS ne sait pas corriger pour relire la suite (une faute de syntaxe, qui arrête la lecture du fichier, ou un autre refus) et à 50 fautes par fichier : corrigez, puis relancez `mjs check`. Un fichier qui n'est pas un composant (un module, une feuille de style) n'a que sa première faute, suivie de la même note ; la faute d'un fichier importé est listée sous ce fichier, et le composant qui l'importe se relit une fois l'import corrigé. Les passes ne relisent que le composant : rien n'est écrit de plus. Une faute que seule la construction entière voit (un fichier cité introuvable, par exemple) n'est pas dans la liste : elle vient une fois le fichier relu sans faute.

**`mjs check --json`** fait la même vérification et la rend en un seul document JSON sur la sortie standard, rien d'autre : les composants compilés, puis chaque erreur et chaque avertissement en objet — gravité, type `[lint.<type>]`, fichier, ligne, colonne, message, ce qu'il faut écrire (`null` quand le message ne le dit pas). Même code de sortie, refus avant compilation compris. Le document part en entier, même dans un tube (`npx --no -- mjs check --json | jq`) ; d'une exception (un `mjs.config.json` illisible, par exemple), `message` porte le message seul, sans la pile — relancez sans `--json` pour la voir. La forme du document : [40 · Travailler avec une IA](40-travailler-avec-une-ia.md). Ses `errors` sont toutes les fautes de la liste, dans le même ordre ; quand il y en a, la clé `listing` donne le nombre de passes de compilation (`passes`) et, pour chaque fichier, son nombre de fautes et la fin de sa liste (`stop` : `complete`, toutes ses fautes ; `unread`, la suite du fichier n'est pas lue ; `limit`, 50 fautes atteintes).

**`mjs check` et `mjs dev` (au démarrage) rétablissent le bloc MJS de `AGENTS.md`** : version mise à jour, bloc retiré remis en fin de fichier, le reste du fichier intact ; sans `AGENTS.md`, ils n'en créent pas, et un bloc mal fermé n'est jamais réécrit (la commande le dit). Le fichier (la cible du lien, s'il en est un) est remplacé d'un seul coup et relu juste avant : changé entre-temps, il n'est pas écrasé. Quand `mjs check`, `mjs dev` ou `mjs init` ajoute ou met à jour ce bloc dans un `AGENTS.md` déjà là, une seconde ligne dit comment l'empêcher : la ligne `<!-- modularjs-agent-rules: off -->`, écrite dans le fichier, le fait laisser tel quel. Détail : [40 · Travailler avec une IA](40-travailler-avec-une-ia.md).

### `mjs build`, `mjs dev`, `mjs serve`

- **`mjs build`** — compile une fois, écrit les fichiers, sort.
- **`mjs dev`** — watch + rechargement à chaud, serveur HTTP+WS sur le port `--port` (défaut **3939**). Un seul `mjs dev` à la fois par projet : le verrou `.mjs-dev.lock` est posé à la racine du projet (le dossier de `mjs.config.json`), même lancé depuis un sous-dossier. `--output`, `--manifest` et `--prod` valent aussi pour le prérendu relancé à chaque sauvegarde.
- **`mjs serve`** — sert le rendu SSR/prérendu par requête (`render.routes`), bloc `render` requis dans `mjs.config.json`, port `--port` (défaut **3000**). Un fichier compilé dont le nom porte l'empreinte du build (`mjs_core-<empreinte>.js`, `<nom>-<empreinte>.css`…) part avec `Cache-Control: public, max-age=31536000, immutable` : son contenu ne change jamais sous ce nom (l'empreinte, cinq caractères ou huit hexadécimaux, est vérifiée sur le contenu du fichier : un nom qui lui ressemble seulement, `photo-2024a.jpg` ou `facture-20241019.pdf`, n'est pas mis en cache pour un an ; `mjs dev` applique la même règle). Tout autre fichier du dossier de sortie — manifeste, carte `.map`, fichier posé à la main — part avec `no-cache`. Un hôte IPv6 (`dev.host: "::1"` ou `"::"`) est accepté. Avec `"outputDir": "."`, `mjs serve` garde la racine du projet comme `mjs dev` (voir plus bas) : ses fichiers privés ne sortent pas, les sorties du build si.

> 🛑 **Une commande mal tapée est refusée.** `mjs biuld`, `mjs serv`… sortent en erreur (**code 1**) sans rien construire, avec la commande la plus proche (`Vouliez-vous dire : mjs build ?`). Un `--root` qui n'existe pas, ou qui désigne un fichier, est refusé de même, en nommant la racine demandée.

> 🛑 **`mjs build` refuse de construire le vide.** Si la racine visée n'a ni `mjs.config.json` ni dossier source — ou si le dossier source existe mais ne contient pas un seul `.mjs` — la commande **sort en erreur (code 1) sans rien écrire**, en nommant le dossier qu'elle a cherché. C'est la protection du **manifeste** : un build sans source écrivait un `µ.paths = {}` par-dessus celui d'un site en place — plus un composant connu, page blanche — en annonçant « ✅ 2 fichiers écrits », code 0. Le cas se produit dès qu'on lance la commande depuis le mauvais dossier, ou qu'on oublie `--root`.

> 🛑 **Un composant qui ne compile pas fait échouer le build.** `mjs build` sort en **code 1** sans rien publier : `bundle.js` n'est pas réécrit, ni les feuilles de mise en page `<composant>.<nom>.css`, ni les fragments de traduction à nom clair (`i18n/<langue>/<section>.json`, en développement ou avec `i18n.hash: false`), ni le registre des variables de thème `.mjs-theme-vars.json` (sans `--prod`), et aucun des fichiers qu'il nomme n'est retiré — le site déjà construit dans ce dossier reste servi tel quel, celui du dernier build réussi, jusqu'à ce que l'erreur soit corrigée. Même règle quand le cœur lui-même ne se construit pas (fichier du runtime absent, `runtime` qui omet un module nécessaire…), en build comme avec `mjs dev` : aucun fichier n'est écrit avec un cœur manquant. `mjs dev`, lui, continue de servir la dernière version valide d'un composant en échec, avec un avertissement (overlay HMR) : le temps de corriger une faute de frappe, le reste du site reste utilisable. Une exception : quand le cœur change au même tour (un autre composant demande une fonction nouvelle), cette version importe l'ancien cœur, que le build retire — elle n'est plus servie, un avertissement le dit. `mjs serve` n'a pas ce filet : la compilation tourne AVANT l'ouverture du port, et la moindre erreur sort en code 1 sans jamais écouter — rien n'est servi tant que l'erreur n'est pas corrigée.

**`mjs dev` surveille le projet où qu'il soit rangé.** Seuls les fichiers et dossiers cachés **du projet** (`.brouillon.mjs`, `.cache/`), `node_modules/` et `.git` sont ignorés : un projet rangé sous un dossier dont le nom commence par un point ou contient `.git` (`~/.projets/app`, un dépôt `moi.github.io`) est surveillé comme un autre, fichiers réunis par le manifeste externe compris (un `vendor/` du projet). Le runtime installé sous `node_modules/` n'est pas surveillé. Par l'API, `await bundler.close()` arrête la surveillance lancée par `bundler.watch()` ; un second `watch()` sur la même instance est refusé tant que le premier n'est pas fermé.

**Un thème fautif ne retire pas les autres.** Un fichier `*.theme.mjs` qui ne compile pas (nom invalide, bloc manquant) est une erreur de construction qui nomme le fichier : `mjs build` échoue sans rien publier, `mjs dev` affiche l'erreur et continue de publier les thèmes du dernier tour réussi, le temps de corriger.

**Une machine très chargée ralentit la construction, sans la faire échouer ; un fichier qui retient le compilateur l'arrête.** Au-delà de 40 fichiers à compiler, la compilation se répartit sur plusieurs fils d'exécution (de deux à huit, selon la mémoire et les processeurs de la machine). Le délai d'un fichier, 60 secondes, compte à partir du moment où un fil le commence : ni l'attente de son tour ni le démarrage du fil n'en font partie. Un fil qui dépasse ce délai, qui ne commence pas le fichier dans le même temps ou qui s'arrête en route est remplacé, et le fichier repart sur un autre fil ; perdu une seconde fois parce qu'un fil ne l'a pas commencé ou s'est arrêté, il est compilé dans le processus principal. Une ligne le dit chaque fois (`… — nouvel essai sur un autre worker`, `… — compilé dans le processus principal`). Avant d'écrire le bilan des avertissements, la commande attend que chaque fil ait rendu ses dernières lignes ; un fil qui ne répond plus est attendu ce même délai de 60 secondes, pas plus, puis arrêté et remplacé : une ligne le dit (`[bundler] un worker ne répond plus depuis 60 s : il est arrêté, ses dernières lignes peuvent manquer`), et le bilan compte les lignes arrivées. Un fichier dont la compilation, commencée, a dépassé le délai n'est jamais compilé dans le processus principal, où rien n'en limiterait ni la durée ni la mémoire : s'il dépasse aussi le délai sur le second fil, ou si ce second essai est perdu autrement, la construction échoue avec une erreur qui le nomme (`la compilation de « carte » a dépassé deux fois le délai de 60 s …`) ; sous `mjs dev`, l'erreur s'affiche comme une erreur de compilation, et la session continue. Quand plus aucun fil ne tient (un fil cassé dès son démarrage : la taille du pool, puis autant de remplaçants, tombent sans rendre un seul fichier), aucun fil n'est relancé : la suite de la construction, ou de la session `mjs dev`, est compilée dans le processus principal, et une seule ligne le dit (`[bundler] plus aucun worker : les fichiers suivants sont compilés dans le processus principal`) ; un fil arrêté sur un fichier trop long ne compte pas parmi ces pertes, des fichiers trop longs ne font donc jamais passer la suite dans le processus principal. Une erreur dans le fichier lui-même n'est jamais reprise : elle fait échouer la construction. Un fichier qui attend la compilation d'un autre (`@import`, `µasset`) l'attend jusqu'à 10 minutes, puis la construction s'arrête en nommant la chaîne d'attente ; une boucle d'imports, elle, est dite tout de suite.

**`mjs dev` regroupe les rafales.** Des fichiers modifiés ensemble (rechercher-remplacer, changement de branche, formateur) donnent une seule reconstruction et un seul rechargement, pas un par fichier.

**`mjs dev` recharge à chaud, et la page garde son état quand l'échange est sûr.** Un changement du seul style d'un composant, ou d'une feuille partagée, s'applique en place, à une exception près : un composant léger posé dans l'ombre fermée d'une balise d'une autre bibliothèque y garde son ancien style jusqu'au rechargement de la page. Un changement du gabarit, du script ou du style d'un composant déjà chargé redessine chacune de ses instances avec le nouveau code, sans recharger la page, quand son script tient dans la liste qui suit (un premier tri, fait à la compilation) et que la page, au moment de l'échange, n'y voit rien qui fausserait l'état gardé (la garde, plus bas) : tout le reste recharge la page. Hors de ses fonctions, le script ne contient alors que des variables `$` dont la valeur de départ s'écrit avec des littéraux, des opérateurs, des tableaux et des objets, et ne lit une variable `$` que telle quelle (`$n = $depart`, `$depart ?= 0`), des dérivées dont le calcul s'écrit avec des littéraux, des lectures de variables `$` du composant et de leur `.length`, des lectures du magasin et de leurs champs (`$$panier`, `$$panier.total`, `$$panier?.total`, `µ.store.panier`, `µlang`) sans `?.` entre `µ`, `store` et la clé, des traductions `µt('cle')` ou `µt('cle', { … })` dont la clé et les valeurs s'écrivent de même, des méthodes de liste qui ne modifient pas leur liste (`filter`, `map`, `find`, `findIndex`, `findLast`, `findLastIndex`, `some`, `every`, `reduce`, `reduceRight`, `includes`, `indexOf`, `lastIndexOf`, `at`, `join`, `slice`, `toSorted`, `toReversed`, `toSpliced`, `with`), appelées sur une variable `$`, une clé du magasin, une liste écrite ou la liste neuve que rend l'une d'elles, avec un rappel simple : une fonction dont le corps est une seule expression de même sorte, qui lit ses paramètres et leurs champs (`(x) -> x.actif`, `(l) -> l.id is $choix`), des opérateurs arithmétiques, logiques et de comparaison, des tableaux et des objets faits de ces éléments, et des ternaires (`$liste = []`, `$filtre = { actif: true }`, `$total = $prix * $quantite`, `$etiquette = "#{$n} sur #{$liste.length}"`, `$etat = if $n > 0 then 'plein' else 'vide'`, `$titre = µt('titre', { n: $n })`, `$somme = $$panier.total * $quantite`, `$visibles = $items.filter((x) -> x.actif)`, `$choisi = ($$listes or []).find((l) -> l.id is $choix)`) ; des fonctions (`inc = -> $count++`, `@fmt = (x) -> …`) ; des constantes dont la valeur est un littéral (`MAX = 10`, `TITRE = 'Panier'`) ; des crochets de vie ; des minuteries de `µevery` ; `@persist` ; `<@window>` et `<@document>` avec leurs écouteurs. Les composants enfants du composant modifié repartent de leur état de départ ; un layout routé (qui porte une `<@view>`) retrouve ainsi la page de l'adresse dans sa vue. Chaque instance garde son état — ses variables `$`, la saisie d'un champ lié, l'étape d'un formulaire, les props reçues de son parent : l'état passe tel quel, sans repasser par le code de l'appli ; une variable nouvelle prend sa valeur de départ, une variable retirée disparaît ; une dérivée dont le texte n'a pas changé garde sa valeur sans être recalculée, tant qu'aucune de ses sources (les variables `$` qu'elle lit, directement ou par une autre dérivée, les clés du magasin qu'elle lit, la langue quand elle traduit) n'a changé depuis son dernier calcul ; l'échange n'écrit ni le magasin, qui n'appartient pas au composant, ni la langue : une dérivée qui lit le magasin ou traduit est recalculée quand une de ses clés du magasin a été écrite depuis son dernier calcul, même sans rendu (`µwrite`) et même pendant l'échange (par l'ancien `µsleep`, l'ancien `µdestroy` ou le script rejoué), quand la langue a changé depuis, ou quand l'instance ne pouvait pas suivre ces changements (instance tenue hors de la page, clé du magasin que son composant ne suit pas, composant que les bascules de langue ne préviennent pas) ; après l'échange, une écriture du magasin ou une bascule de langue la recalcule comme avant ; une dérivée modifiée ou nouvelle, jamais calculée, qui lit une variable nouvelle ou une dérivée modifiée, ou dont une source a été écrite depuis son dernier calcul, est recalculée une fois, à sa première lecture ; un gestionnaire modifié sert dès le clic suivant. Ce qui est refait à l'échange, et seulement cela : le calcul de ces dérivées, le gabarit redessiné (il relit ses valeurs), les crochets de départ et d'arrivée décrits ci-dessous ; ce qu'une valeur fait quand on la lit — par `valueOf`, `toString` ou un Proxy rangé dans une variable `$` ou dans le magasin, ou dans l'un de leurs éléments (un champ lu par un rappel, un élément que `join` ou `toSorted` convertit) — elle le refait alors, comme quand une de ses sources change. Une dérivée qui appelle une méthode de liste n'est échangée que si chaque valeur qu'elle lit, directement, par une autre dérivée ou par la valeur de départ d'une variable nouvelle (variable `$`, clé du magasin et ses champs), est une valeur simple, une vraie liste (sans méthode ni `constructor` à elle) ou un objet qui ne porte aucune de ces méthodes, et si les méthodes du langage n'ont pas été remplacées : sinon la page se recharge avant le départ de l'ancienne instance, ni `µsleep` ni `µdestroy` ne jouent et aucune méthode de l'appli n'est appelée (une variable `$` qui tient un objet de l'appli muni de sa propre méthode `filter`, par exemple). Deux cas ne s'inspectent pas sans appeler l'appli : une liste enveloppée d'un Proxy, que la vérification prend pour une vraie liste (`Array.isArray` la dit liste) en appelant ses trappes, que le calcul appelle de nouveau, et l'accesseur d'un élément, que le calcul de la dérivée appelle. Une instance redessinée part comme d'un retrait de la page (`µsleep`, `µdestroy`, nettoyage des `:attach`), puis revient comme une arrivée : `µawake` et `µmount` jouent de nouveau, avec le nouveau code, et ce que l'ancien `µmount` avait ouvert (minuterie, écouteur, bibliothèque posée sur un nœud) doit être rendu par l'ancien `µdestroy` — gardez dans une variable `$` ce que l'un passe à l'autre (`$t = µevery …` dans `µmount`, `$t()` dans `µdestroy`). Les composants enfants que dessine son gabarit sont recréés et repartent de leur état de départ, avec les props que le parent leur passe ; les autres composants de la page ne bougent pas, la page non plus (défilement, focus hors du composant). Une page quittée que le routeur garde en mémoire est redessinée de même à son retour, avec le nouveau code et son état. Un composant revenu au texte d'une version déjà chargée s'échange comme les autres. Une sauvegarde sans changement ne fait rien ; des sauvegardes rapprochées donnent un seul échange quand la suivante arrive pendant la compilation de la précédente, sinon des échanges successifs qui gardent chacun l'état. Le terminal dit ce que la page a fait, d'après sa réponse : « rechargé à chaud, état gardé » pour un échange que la page a mené à son terme sans plantage pendant sa veille (plus bas), « la page s'est rechargée en entier » quand elle n'a pas pu échanger ou y a renoncé, rien quand aucune page n'est ouverte. La page se recharge en entier, comme pour tout autre fichier, dès que le script sort de cette liste, même quand seul le gabarit change : un appel dans une valeur de départ ou une dérivée, même d'une lecture (`Math.max(…)`, `Object.keys($objet)`, `$liste.filter(…)` dans une valeur de départ), hormis une traduction `µt(…)` ou une méthode de liste admise dans une dérivée — une traduction qui ne lit ni variable `$` ni magasin est une valeur de départ, rejouée à chaque échange, et `$titre = µt('titre')` recharge donc la page ; une traduction avec un troisième argument ; une traduction ou une lecture du magasin écrite avec `?.` sur `µ`, `µ.t` ou `µ.store` (`µ?.t('cle')`, `µ.store?.panier`) ; une méthode qui modifie sa liste (`sort`, `reverse`, `splice`, `push`, `pop`, `shift`, `unshift`, `fill`, `copyWithin`), `concat`, `flat`, `flatMap` ou `forEach` ; un rappel qui n'est pas simple (corps de plusieurs instructions, affectation, appel d'une fonction, nom passé à la place d'une fonction comme `$liste.map(String)`, paramètre décomposé) ; une méthode de liste appelée sur ce que lit un rappel (`(x) -> x.tags.includes('a')`) ou sur un élément (`$liste.find(…).filter(…)`) ; la lecture d'un champ (`window.reglages.largeur`, `$objet.nom`, un magasin importé `µ$$compte.value` : seuls la `.length` d'une variable `$` et les champs du magasin `$$` sont permis, et dans une dérivée la `.length` d'une liste neuve et les champs des paramètres d'un rappel), d'une constante ou d'une variable ordinaire ; un étalement (`[...$liste]`) ; une chaîne gabarit qui insère autre chose qu'une variable `$` ou sa longueur ; un objet avec accesseur ou méthode ; une variable ordinaire au haut du script, qu'un gestionnaire, un crochet ou le gabarit réécrit (`prochain = 1` puis `prochain++`, une référence `:this=!{canvas}`) ; une constante qui n'est pas un littéral (`liste = []`, `CONF = { pas: 2 }`) ; un reffet (`µeffect`) ; tout autre appel ou instruction hors des fonctions (minuterie, écouteur, variable globale, magasin) ; une valeur de départ qui calcule sur une variable `$` ; une valeur de départ ou une constante changée (`$count = 0` devenu `$count = 5`, `MAX = 10` devenu `MAX = 20`) ; et toujours au moindre doute : un module partagé changé (`.civet`, `.coffee`) que ne relit aucun composant échangé au même tour, ou qui déclare ou lit un magasin, ou pose un `µeffect` (paragraphe suivant), un composant ajouté, retiré ou renommé, un crochet de vie modifié (`µmount`, `µdestroy`, `µawake`, `µsleep`, `µurlChange`…), une règle ou un type de variable, ou une règle de magasin, changé (`<vars>`), un slot ajouté, retiré ou renommé, `@formAssociated` posé ou retiré, une instance légère (`mjs-light`) ou à slots indexés, un cœur qui change au même tour (le composant demande une fonction nouvelle du runtime), une feuille partagée changée avec le composant, `js: "bundle"` ou `css: "split"`. La garde, au moment de l'échange : la page relève les champs propres de chaque instance juste après son script, dernier pas de sa construction (pour une instance que `:wake` fait attendre, après le script joué à son réveil), puis de nouveau après chaque échange. Elle en écarte l'état `$` et les seuls champs que le cœur et le code compilé écrivent eux-mêmes sur une instance (une liste de noms exacte, jamais un préfixe) ; tout autre champ est gardé : une fonction `@fmt = (x) -> …`, un écouteur de `<@window>`, un champ au nom qui ressemble à un nom interne (`@_mjsFmt`, `@_gl_1`). Un champ gardé écrit, retiré ou ajouté depuis le relevé recharge la page, même quand seul le gabarit change, qu'il vienne du composant (un gestionnaire, un crochet comme `µmount`, le gabarit ; par `@['fmt'] = …`, `Object.assign(this, …)`, un alias `moi = this`, `Object.defineProperty`, `Reflect.set`) ou du dehors (`e = document.createElement('mjs-carte')` puis `e.fmt = …` avant de l'insérer dans la page) : le nouveau script remettrait ce champ à son départ, l'instance garderait un état faux. La garde compare chaque champ à son relevé, valeur (le même objet, la même fonction) et description (accesseurs, écriture, énumération) ; elle ne voit pas ce qui ne change ni l'une ni l'autre : une fonction ou un objet modifié en place (`@fmt.cache = {}`, `@routes[0].titre = …` : le champ tient toujours le même objet), ni un champ que la nouvelle version ne pose plus, qui reste sur l'instance avec sa valeur d'avant. La page veille aussi sur les plantages, de l'échange à la fin d'une fenêtre fixe : les microtâches de l'échange (premier rendu, crochets rejoués), puis les minuteries de délai 0 que ces crochets ont posées (`setTimeout(f, 0)`, `setTimeout(f)`), puis une tâche encore. Une erreur levée pendant cette fenêtre, par le composant ou par tout autre code de la page, qu'elle soit prise par le rendu (le nouveau gabarit lit `$o.a` alors que l'état gardé tient `$o` à `null`) ou par personne, et une promesse rejetée sans traitement (un `µmount` qui rend `Promise.reject(…)`) rechargent la page : le nouveau code s'y affiche, avec un état neuf. Ce qui arrive plus tard n'est pas couvert, même posé par un crochet rejoué : une minuterie plus longue, même d'1 ms, une image (`requestAnimationFrame`), un événement ; son erreur s'affiche dans la console, sans recharger la page. La page ne répond au terminal qu'à la fin de cette fenêtre ; dans un onglet caché, où le navigateur espace les minuteries, la réponse arrive d'autant plus tard. Une instance tenue hors de la page pendant l'échange (page gardée par le routeur) est veillée de même quand elle revient, redessinée. Ce qui revient après un rechargement complet : la position de défilement et les variables `@persist` ([3 · Réactivité](03-reactivite.md)). Une erreur de compilation laisse la page sur la dernière version valide et s'affiche par-dessus ; corrigée, l'affichage part et le changement suit les règles ci-dessus (à chaud, ou rechargement complet) ; annulée en revenant au texte d'avant l'erreur, dans un composant comme dans une feuille partagée, seul l'affichage part, la page ne se recharge pas et garde son état. Rien de ce mécanisme n'entre dans un build de production.

**Les traductions, les modules et les classes suivent aussi, sans recharger la page.** Un fichier de traduction de la racine (`i18n/<langue>.yml`, `.yaml` ou `.json`) changé : la page reprend les textes de cette langue et redessine les composants qui traduisent, chacun avec son état ; une dérivée qui traduit est recalculée. Une section (`i18n/<langue>/<section>.yml`) garde son adresse d'un tour à l'autre : la page se recharge pour la relire. Un module (`.civet`, `.coffee`) ou une classe (`Nom.class.mjs`) changé : les composants qui l'importent, ou qui citent la classe, sont échangés comme si leur texte avait changé, avec les règles ci-dessus, et le nouveau module se charge pour eux ; le haut du module ou de la classe est rejoué, ce qu'il tenait (un cache, un membre de la classe écrit depuis) repart de sa valeur de départ. La page se recharge en entier quand un composant qui l'importe ne s'échange pas, quand autre chose qu'un composant échangé le relit (un `µimport` fait à l'exécution, le manifeste), ou quand le module déclare ou lit un magasin, ou pose un `µeffect` : rejoué, il le déclarerait une seconde fois.

**La page peut être servie par un autre serveur (Rails, par exemple).** Elle demande alors le client de rechargement au port de `mjs dev` (`<script src="http://127.0.0.1:3939/__mjs_hmr/client.js"></script>`, à n'écrire que dans la page de développement) et ses fichiers compilés à son propre serveur, aux adresses du manifeste : le client se connecte à l'adresse d'où il vient, et chaque échange importe les nouveaux fichiers comme la page l'a fait au départ. L'origine de la page doit être locale (`localhost`, `127.0.0.1`…) ou écrite dans `dev.allowedHosts` (plus bas). Un échange ne touche pas à l'adresse de la page : la route reste celle où vous êtes ; seul un rechargement complet la relit, auprès du serveur qui sert la page.

**`mjs dev` sert aussi la page du projet.** Sans bloc `render`, tout chemin qui n'est pas un fichier compilé (`urlPrefix`) est cherché dans la racine du projet (le dossier de `mjs.config.json`, ou `--root`) : `/` et tout chemin finissant par `/` servent l'`index.html` de ce dossier, sinon le fichier demandé, avec son type MIME. Ce qu'un navigateur charge sort de la racine — pages, feuilles, scripts (`.js`, modules `.mjs`), données (`.json` rangé dans un dossier, `.csv`, `.md`, `.txt`, `.xml`), cartes `.map`, sous-titres `.vtt`, images, polices, modèles 3D (`.glb`, `.gltf`), sons, vidéos, `.wasm`, `.pdf`… —, les secrets d'une appli voisine jamais. Jamais servis : un fichier ou un dossier caché (`.git`, `.env`…) ; les dossiers `config/`, `log/`, `logs/`, `tmp/`, `db/`, `storage/`, `node_modules/` à toute profondeur, `app/` et `server/` à la racine (sources de l'appli et du serveur) ; les fichiers serveur `*.server.*`, `mjs.config.json`, `package.json` et les fichiers de configuration voisins (`package-lock.json`, `tsconfig.json`, `composer.json`…) ; à la racine même, tout `.json` (`secrets.json`, `credentials.json`, un `manifest.json` aussi : rangez dans un dossier, `public/` par exemple, le JSON que la page charge) ; les entrées serveur : `ws.js` et `game.js` à la racine (cherchées par `mjs ws` et `mjs server`), `server.js`, `server.mjs` et `serveur.js` à la racine (l'entrée habituelle d'une appli Node, en anglais ou en français) et, rangées n'importe où sous n'importe quel nom, les entrées déclarées par `ws.entry`, `server.entry` et `render.entry` ; les clés et certificats (`.key`, `.pem`, `.p12`…), la configuration (`.env`, `.yml`, `.toml`, `.ini`, `.lock`…), les sources serveur (`.rb`, `.php`, `.py`, `.ts`, `.cjs`, `.civet`…), les journaux, bases et sauvegardes (`.log`, `.sql`, `.sqlite`, `.bak`…) ; un fichier sans extension (`Gemfile`, `id_rsa`). Les noms se comparent comme les lit un disque macOS ou Windows, sans la casse et sans les points ou espaces de fin : `/Config/default.json` est refusé comme `/config/default.json`. Un lien symbolique qui sortirait de la racine, ou qui mènerait à un fichier refusé, répond 404. Un module serveur qui n'est pas une entrée déclarée reste servi s'il est rangé ailleurs que sous `server/` (`lib/db.mjs`, par exemple), comme une entrée passée seulement par `--entry` : rangez-les sous `server/`. Une page HTML servie ainsi reçoit le client de rechargement quand il est actif ; il se connecte en `wss:` quand son script est chargé en https (un tunnel, par exemple), en `ws:` sinon. Avec un bloc `render`, `render.routes` garde la main, et chacune de ses pages reçoit le même client, quel que soit son mode (rendu serveur, client seul, prérendu, page en flux) : une sauvegarde y joue comme ailleurs, échange à chaud ou rechargement. `mjs serve` ne pose jamais ce client. La même garde vaut pour les fichiers compilés quand `outputDir` est la racine du projet elle-même (`"outputDir": "."`) : `/modularjs/secrets.json` est refusé comme `/secrets.json` ; un dossier de sortie dédié (`public/modularjs`, le défaut) reste servi tel quel. Les sorties que le build écrit lui-même y restent servies, reconnues à leur contenu : la liste de pré-cache `mjs-precache.json`, les fichiers de messages `mjs_err-<langue>-<empreinte>.json` et tout fichier dont l'empreinte est vérifiée, le manifeste et les feuilles marqués `/* @generated by ModularJS */`. `mjs serve` applique la même garde.

**Un dossier de sortie qui contient la racine du projet est refusé.** `"outputDir": ".."` (ou `--output` vers un dossier parent) ferait servir par `mjs dev` et `mjs serve` tout ce dossier, les fichiers privés d'une application voisine compris : `mjs build`, `mjs dev` et `mjs serve` s'arrêtent dès le départ, avant toute compilation, avec un message qui nomme le dossier. Donnez à `outputDir` un dossier dans le projet (`public/modularjs`, le défaut) ; la racine elle-même (`"outputDir": "."`) reste permise.

**Un dossier de sortie ne sert qu'un projet.** Chaque construction retire d'`outputDir` les anciennes versions des fichiers qu'elle écrit, sans savoir qu'un autre projet s'en sert : quand deux projets partagent ce dossier, reconstruire l'un retire des fichiers que le manifeste de l'autre nomme encore, et les pages de l'autre ne les trouvent plus. Donnez à chaque projet son propre `outputDir`.

**`mjs dev` ne répond qu'à ses propres noms.** Une requête dont l'en-tête `Host` n'est ni `localhost` ou l'un de ses sous-domaines (`app.localhost`, toujours en boucle locale), ni `127.0.0.1`, ni `[::1]`, ni le nom de la machine (ou `<nom>.local`), ni l'hôte de `dev.host` répond **403**, sur toutes les routes : c'est la parade au rebinding DNS (une page web dont le nom bascule vers `127.0.0.1` pour lire votre serveur de développement). Avec `dev.host: "0.0.0.0"` (ou `"::"`), les adresses de la machine sont acceptées aussi : un téléphone du réseau local ouvre `http://192.168.x.x:3939`. Le client de rechargement se connecte alors par l'adresse que la page a utilisée, et sa connexion est acceptée — une page du réseau local n'est jamais acceptée tant que le serveur n'écoute qu'en local. Le rechargement à chaud et les formulaires (actions `.server.mjs`) acceptent la page dont l'origine est la même que l'en-tête `Host` reçu (la page servie par cette connexion, sous l'un de ces noms), et toute page locale : une origine `localhost` ou l'un de ses sous-domaines (`http://app.localhost:3939`), `127.0.0.1` ou `[::1]`, sur n'importe quel port (une autre appli de la machine), même derrière un proxy local qui réécrit `Host`. Le nom de la machine, `<nom>.local` et les adresses du réseau ne font pas une origine locale : dans `Host`, ils disent que la requête arrive ici ; dans l'origine d'une page, ils ne prouvent pas qu'elle vient d'ici (un nom du réseau local se contrefait). Une page servie sous ces noms est donc acceptée de même origine, pas depuis un autre port ni derrière un proxy qui réécrit `Host`.

**Un tunnel ou un proxy s'ouvre par `dev.allowedHosts`, qu'il garde l'en-tête `Host` ou qu'il le réécrive.** Un tunnel (`abc.ngrok-free.app`) ou un proxy de développement qui garde l'en-tête `Host` (Caddy, Traefik, conteneur) reçoit 403 tant que son nom n'est pas déclaré : `"dev": { "allowedHosts": ["abc.ngrok-free.app"] }`. Un nom qui commence par un point couvre ce domaine et ses sous-domaines (`[".ngrok-free.app"]`) ; `true` accepte tous les noms dans `Host` et lève donc la parade. Le 403 cite le nom refusé et la ligne à écrire. La page servie sous un nom déclaré, par un tunnel qui garde `Host`, est acceptée par le rechargement à chaud et par les formulaires (actions `.server.mjs`), même quand le serveur n'écoute qu'en local : son origine est la même que `Host`. Une page dont l'origine diffère de `Host` reste refusée, `true` compris : `true` accepte tous les noms dans `Host`, pas toutes les origines — sans quoi n'importe quel site ouvert dans votre navigateur pourrait écouter le rechargement et envoyer vos formulaires. Un tunnel qui réécrit `Host` en `localhost` (`ngrok http 3939 --host-header=rewrite`, par exemple) passe la garde `Host` sans rien déclarer, mais la page qu'il sert garde le nom du tunnel pour origine : déclarez ce nom **exact**, `"dev": { "allowedHosts": ["abc.ngrok-free.app"] }`. Derrière un `Host` réécrit, ni `true` ni une entrée `.domaine` n'admettent l'origine : sur un domaine partagé (`.ngrok-free.app`), l'entrée admettrait aussi la page de n'importe quel autre utilisateur de ce domaine ouverte dans votre navigateur, qui pourrait écouter le rechargement et envoyer vos formulaires. `mjs dev` refuse alors la page ; quand l'en-tête `Host` reçu est local (`localhost`, `127.0.0.1`, `[::1]` : un tunnel l'a réécrit) et qu'une entrée `.domaine` couvre l'origine, son terminal (comme la réponse 403 d'un formulaire) dit le nom exact à écrire — pour vingt noms au plus dans le terminal, puis une ligne dit que les refus suivants n'y sont plus affichés. Sous un `Host` gardé, la page d'un autre utilisateur du domaine reçoit un refus simple, sans nom à écrire. Le client de rechargement se connecte à l'adresse d'où son script est chargé : derrière un tunnel, il passe par le tunnel. `mjs serve` ne lit pas `dev.allowedHosts` : ses formulaires s'ouvrent à une autre origine par `render.allowedOrigins` ([21 · Navigation](21-navigation.md)). Une valeur d'une autre forme (chaîne seule, `http://…`, nom suivi d'un port) est refusée à la lecture de la configuration.

**L'atelier n'enregistre dans le source que depuis la machine elle-même.** Son interrupteur « enregistrer » (atelier des thèmes, `/__mjs/theme`, cf. [34 · Déboguer](34-deboguer.md) §3) écrit la couleur dans le fichier qui la déclare : seule une page ouverte sur cette machine y parvient (`localhost` ou l'un de ses sous-domaines comme `app.localhost`, `127.0.0.1`, `[::1]`). Un autre poste du réseau (`dev.host: "0.0.0.0"`, un téléphone) reçoit un refus (403) et rien n'est écrit ; de même pour ce qui arrive par un mandataire qui se signale (en-têtes `Forwarded`, `X-Forwarded-For`, `Via`…). Un tunnel brut vers `mjs dev` (`ssh -R`, `socat`) ne pose aucun en-tête : il passe pour la machine elle-même, n'en ouvrez donc pas vers un réseau que vous ne tenez pas. Un mandataire qui ne pose aucun de ces en-têtes (le réglage par défaut de nginx et de HAProxy) passe, lui aussi, pour la machine. Un fichier d'un dossier caché (`.git`…) ou de `node_modules` n'est jamais réécrit.

Le rendu piloté par la config (`render`, SSR, prérendu) est détaillé au chapitre [19 · SSR](19-ssr.md) — pas repris ici.

### `mjs ws` et `mjs server`

- **`mjs ws`** — lance le serveur temps réel (MJS-WS). Détail complet : [23 · MJS-WS](23-mjs-ws.md).
- **`mjs server`** — lance le serveur de jeu (MJS-Server, composé par-dessus MJS-WS). Détail complet : [24 · MJS-Server](24-mjs-server.md).

### `mjs mcp`

Lance le serveur MCP (Model Context Protocol) de MJS en stdio, pour un assistant d'IA qui le démarre lui-même dans le dossier du projet : chercher dans la doc de la version installée et en lire une page, compiler un composant sans rien écrire, lire les erreurs de la page d'un `mjs dev` en cours, lister les composants et les routes. La sortie standard est au protocole ; le serveur s'arrête quand son entrée se ferme, en code 0 (ce qui a déjà été reçu a encore une seconde pour être servi). Gardes : une recherche compte 20 mots et 500 caractères au plus ; un lien symbolique qui mène hors du projet ou de la doc n'est pas suivi ; le jeton du journal (`journal.viewer`) ne part que vers le `mjs dev` du projet, sur la boucle locale (`127.0.0.1`, `::1`, `localhost`), à son port. Les outils et leur déclaration : [40 · Travailler avec une IA](40-travailler-avec-une-ia.md).

### Arrêter un serveur (Ctrl+C)

`mjs dev`, `mjs serve`, `mjs ws` et `mjs server` s'arrêtent proprement sur **Ctrl+C** (ou un `SIGTERM`) : la page ou la réponse en cours se termine d'abord, **20 s** au plus, puis le programme sort en code 0. Sans rien en cours, l'arrêt est immédiat.

- **Forcer l'arrêt** : un **2ᵉ Ctrl+C**, plus d'une seconde après le premier, coupe tout de suite sans attendre les réponses en cours. Quand l'arrêt dure, le terminal le rappelle : `arrêt en cours — Ctrl+C à nouveau pour couper tout de suite`.
- Un 2ᵉ Ctrl+C **dans la même seconde** est ignoré : c'est souvent le même Ctrl+C reçu deux fois (`npm run` le relaie à son programme, `tsx` aussi quand on lance depuis les sources). Sans cette seconde de tolérance, un seul Ctrl+C couperait les pages en cours.

**Rechargement de `mjs ws` et `mjs server`.** Le fichier d'entrée est surveillé : une modification relance le serveur. Le `setup()` de la nouvelle version tourne **avant** l'arrêt de l'ancienne : s'il jette (variable d'environnement manquante, faute), l'ancienne version reste en service et l'erreur est affichée. En production (`NODE_ENV=production`), le fichier d'entrée n'est pas surveillé : un déploiement redémarre le service. Les fichiers serveur compilés vont dans `node_modules/.cache/mjs/server/` du projet ; rien ne s'écrit ailleurs, et un paquet importé par `@import` est résolu par Node lui-même, comme pour un fichier du projet (`node_modules` du projet, puis celui de chaque dossier parent). Sans `node_modules` dans le projet, ou s'il est en lecture seule, ils vont dans `mjs-server-cache-<uid>` du dossier temporaire, créé en `0700`, dans un sous-dossier propre au projet où des liens `node_modules` rendent à Node ces mêmes dossiers ; un dossier de ce nom qui n'est pas à vous, qui est un lien ou que d'autres peuvent écrire est refusé.

`mjs ws` et `mjs server` acceptent en plus `--host <adresse>` (ou `ws.host`/`server.host` dans `mjs.config.json` selon la commande, `--host` prioritaire) — sans l'un ni l'autre, le transport écoute en local (`127.0.0.1`, MÊME défaut que le pont). Qui veut exposer le serveur le dit explicitement avec `--host ::`. `--port` (comme `ws.port`/`server.port`) est validé **entier 1-65535** : hors bornes, la commande sort en erreur avant même de tenter d'ouvrir le port.

### Drapeaux communs

| Drapeau | Rôle |
|---|---|
| `--root <dossier>` | racine du projet (défaut : répertoire courant) |
| `--manifest <chemin>` | chemin du bundle (point d'entrée), remplace `manifestPath` — mêmes refus : jamais un fichier source, ni, quand la construction écrit dans le dossier des sources, un fichier existant qui ne porte pas la marque des fichiers produits (code 1, rien n'est écrit) |
| `--output <chemin>` | répertoire de sortie des fichiers compilés, remplace `outputDir` |
| `--entry <chemin>` | fichier d'entry du serveur (`mjs ws`/`mjs server`), défauts propres à chaque commande |
| `--host <adresse>` | hôte d'écoute — `mjs ws`/`mjs server` (défaut `127.0.0.1`, `--host ::` pour toutes les interfaces) |
| `--port <n>` | port du serveur — `mjs dev` (3939), `mjs serve` (3000), `mjs ws` (4000), `mjs server` (4001) |
| `--once` | force la commande sur `build` (compile et sort) |
| `--dev` | build de **développement** — panneau d'inspection embarqué, non minifié (sauf `"minify": true`), cartes de source (c'est le défaut) |
| `--prod` | build de **production** — minifié (sauf `"minify": false`), fragments i18n hachés, aucun outil de développement |
| `--cache`, `--cache=verify` | `mjs build` seulement : ne recompile que les fichiers changés depuis la construction précédente, production comprise, pour une sortie identique à l'octet à une construction complète ; `--cache=verify` la compare ensuite à une construction complète faite à part (cf. « Construction rapide » plus bas) ; les autres commandes l'ignorent, avec un avertissement |
| `--derived` | `mjs check` seulement : après la liste des composants, dit le mode de l'appli — la précision (défaut) ou la règle de l'horloge (`"derived": "clock"`, cf. la table de configuration plus bas) — puis classe chaque valeur dérivée de chaque fichier — **précise** quand le compilateur prouve ce qu'elle lit (variables `$` du composant, autres dérivées précises, littéraux, opérateurs, champs lus, liste courte de méthodes et de fonctions du langage, cf. [3](03-reactivite.md)) et que son calcul coûte (appel de méthode, appel sur une liste étalée, liste ou objet bâti, ou lue par une valeur précise), **horloge** sinon (variable ordinaire changée ailleurs, fonction importée, `window`, `Date.now()`, propriété `@x`, variable `$` qui reçoit un objet que le script garde ailleurs — `$l = garde`, « objet gardé par le script » —, ou forme hors de la liste courte : fonction du `<script>`, magasin `$$`, contexte `§§`…, ou calcul simple : lectures et opérateurs, refaits plus vite que vérifiés), avec la raison —, puis le total. Une valeur précise suit ses sources, sauf quand elle repasse à l'horloge (cf. [3](03-reactivite.md)) : après huit vérifications de suite qui n'ont pas servi, dans le doute à l'exécution, ou après `µrefresh($x)` sur une variable qu'elle lit, elle est refaite après toute écriture du composant ; avec `"derived": "clock"`, toutes les valeurs dérivées du code produit sont refaites à leur lecture après toute écriture du composant, et le classement dit ce que la précision changerait ; sans `--derived`, la sortie de `mjs check` reste la même ; les autres commandes l'ignorent, avec un avertissement |
| `--json` | `mjs check` seulement : un seul document JSON sur la sortie standard, à la place des lignes habituelles — les composants compilés, chaque erreur et chaque avertissement en objet (gravité, type, fichier, ligne, colonne, message, ce qu'il faut écrire), même code de sortie ; avec `--derived`, le classement des dérivées en plus ; les autres commandes l'ignorent, avec un avertissement |
| `-v`, `--version` | affiche la version du paquet mjs (`mjs <version>`) et sort — répond depuis n'importe quel dossier, sans config ni projet |
| `-h`, `--help` | affiche l'aide et sort |

`mjs build`, `mjs check`, `mjs dev` et `mjs serve` annoncent en clair le mode retenu et d'où il vient — c'est cette ligne qu'on relit dans un journal de déploiement pour vérifier qu'on a bien construit ce qu'on croit.

### Sur ma machine, en développement ; sur le serveur, en production

**Un build est en développement, sauf si on demande le contraire.** Non minifié, panneau d'inspection embarqué, cartes de source, fragments i18n aux noms lisibles : c'est ce qu'on veut sur son poste, et c'est ce qu'on obtient sans rien configurer. Avec `"minify": true`, le fichier est minifié, et rien d'autre ne change.

Le **serveur**, lui, ne se devine pas. Le framework ne regarde ni le nom d'hôte, ni le port, ni l'adresse, ni aucune variable d'environnement : `mjs build` lancé par un script de déploiement sur un shell non interactif produit exactement ce qu'il produit sur un portable. **C'est au script de déploiement de le dire**, et il n'y a qu'une façon :

```bash
mjs build --prod
```

Une seule ligne, dans un seul fichier — celui qui déploie. Rien de versionné ne peut se tromper de machine, et aucune variable héritée d'un shell ne peut basculer un build sans qu'on l'ait demandé.

> ⚠️ Sans `--prod`, le déploiement pousse un build de développement en ligne : bundle non minifié (minifié avec `"minify": true`, le reste ne change pas), `window.µ` exposé, panneau d'inspection livré aux visiteurs, et **fragments i18n non hachés** — donc servis depuis le cache des navigateurs après une correction de traduction. Le bandeau imprimé par `mjs build` (« 🛠️ Build de DÉVELOPPEMENT… ») l'écrit noir sur blanc dans le journal de déploiement : c'est la ligne à relire en cas de doute.

Cette indifférence à l'environnement ne vaut que pour le CHOIX DU BUILD (minification, panneau d'inspection embarqué) — la garde des routes de développement, décrite juste en dessous, accepte elle aussi `NODE_ENV=production` comme signal, en plus de `--prod`.

Les routes de développement que `mjs dev`/`mjs serve` exposent — l'atelier de variables de thème (`GET /__mjs/theme`, [34 · Déboguer](34-deboguer.md) §3) et le journal d'erreurs (`GET /__mjs/errors`, [19 · SSR](19-ssr.md) § *Journal d'erreurs*) — suivent une garde complémentaire : ces routes sont fermées dès que la commande tourne avec `--prod`, et aussi quand `NODE_ENV=production` est posé, même sans `--prod` — sauf le journal ouvert par son jeton (`journal.viewer` en chaîne), exigé alors en toute circonstance. Ces deux pages appellent des fonctions du cœur (crochets de vie, blocs `{if}` et `{for}`, mutations profondes) : si votre cœur est nu (`"runtime": "core"`), la page de la visionneuse les apporte elle-même, celles que votre cœur n'a pas, sans rien ajouter à votre cœur ni à son poids ; s'il est minifié (`minify: true`, ou la production), elle les appelle par les noms courts de la construction.

### Construction rapide : `mjs build --cache`

`mjs build --cache` garde ce que la construction a compilé, et la suivante ne recompile que les fichiers changés depuis. La sortie est identique à l'octet à celle d'une construction complète, dans un dossier de sortie neuf comme sur place, en développement comme en production. Sans `--cache`, rien ne change : tout se recompile, aucun cache n'est lu ni écrit.

```bash
mjs build --cache                    # développement
mjs build --prod --cache             # production
mjs build --prod --cache=verify    # puis comparée à une construction complète
```

- **Où vit le cache.** Dans `node_modules/.cache/mjs/build/` du projet : un fichier par clé (`<clé>.json`), le dossier `files/` (les fichiers compilés, nommés par leur contenu, qu'un dossier de sortie neuf reprend sans rien recompiler) et `last.json` (ce qu'était la clé du dernier passage, pour dire ce qui a changé). Sans dossier `node_modules` au projet, rien n'est créé et la construction est complète. Le cache n'est écrit qu'après une construction sans erreur : un tour en échec laisse celui d'avant intact.
- **Ce que la clé suit.** La version du framework (ses fichiers, et les versions de Node, esbuild, Civet, CoffeeScript, Sass et acorn), `mjs.config.json` entier, et les options de la construction (développement ou production, minification, modes `js` et `css`, préfixe d'adresse, cartes de source). Le dossier de sortie et le manifeste n'y entrent pas : `--output` vers un dossier neuf reprend le même cache. Sous une clé, chaque fichier est suivi par son contenu et par celui de ce qu'il lit (partiels, modules importés, fichiers de types et d'effets, images de ses `µasset`) : quand l'un change, ce fichier et ceux qui le lisent se recompilent. Les traductions (`.yml`) n'entrent dans aucun fichier compilé : les fichiers de messages sont refaits à chaque construction.
- **La ligne de bilan.** Chaque construction sous `--cache` l'écrit : `cache : 566 fichiers repris, 1 recompilé`, ou `cache écarté — <raison> : construction complète (567 fichiers compilés)`, la raison étant `premier passage`, `mjs.config.json a changé`, `nouvelle version du framework`, `options de la construction changées`, `fichier du cache illisible` ou `aucun dossier node_modules`.
- **Quatre clés gardées.** Les quatre clés servies le plus récemment restent : une configuration déjà vue parmi elles retrouve son cache. `files/` ne garde que les fichiers que ces quatre clés citent.
- **En production** (`--prod --cache`), le cache est à part de celui du développement. Les noms courts que la minification donne aux propriétés internes du framework dépendent de l'ordre des fichiers et de tout ce qui les précède : un fichier repris n'est servi que si une construction complète lui donnerait exactement les mêmes noms, sinon il est recompilé à sa place. La sortie reste identique à l'octet à celle de `mjs build --prod`, `.mangle-cache.json` compris, dans un dossier neuf (sans `.mangle-cache.json`) comme sur place (avec celui de la construction d'avant). Un changement qui déplace les noms de tous les fichiers recompile beaucoup, parfois tout : le premier composant dans l'ordre des noms, un fichier qui fait entrer une nouvelle brique dans le cœur, ou un cache écrit sur place puis lu par une construction en dossier neuf. Le cache sert le plus quand vous gardez la même habitude d'une construction à l'autre : toujours un dossier neuf, ou toujours sur place. Si la recompilation d'un fichier en demande un autre déjà passé dans cet ordre, la construction s'arrête avec un message plutôt que de donner d'autres noms courts : relancez sans `--cache`.
- **`--cache=verify`.** La même construction, puis une construction complète sans le cache, faite à part (dans un dossier retiré ensuite) et partie du même `.mangle-cache.json` ; chacun de ses fichiers est comparé à l'octet à celui de la construction servie. Égaux : `cache vérifié : 2142 fichiers identiques à l'octet`. Au moindre écart, le cache est jeté, les fichiers en écart sont nommés, et la construction complète est refaite sur place : la sortie devient exactement celle de `mjs build`, pages prérendues comprises, et les fichiers en trop en sont retirés comme à toute construction (seulement ceux que le registre `.mjs-outputs.json` dit écrits par une construction) ; puis la commande sort en code 1, et la construction suivante recompile tout.
- **Le prérendu** (bloc `render`) est servi par le même cache en développement, avec sa propre ligne, `Prérendu — cache : …`. En production, et sous `--cache=verify`, il recompile tout.
- **Limites.** Un fichier de `files/` abîmé à la main est servi tel quel par la construction suivante : `--cache=verify` le voit et jette le cache. Avec `"js": "bundle"`, sur place, quand le cache a été écrit entre-temps par une construction faite ailleurs (`--output`), l'ancienne image d'un `µasset` changé reste dans le dossier de sortie, citée par aucun fichier, jusqu'à la construction complète suivante. Le cache de `--cache` vaut du code : ne le reprenez que d'une source sûre.
- **`mjs dev` ne lit pas ce cache** : il garde le sien en mémoire pendant toute la session, et ce que `mjs build --cache` écrit sous `node_modules/.cache` ne relance aucun tour. `--cache` avec une autre commande que `mjs build` est ignoré, et la commande le dit.
- **Vider le cache** : `rm -rf node_modules/.cache/mjs/build`, et la construction suivante est complète. Pour un doute sur le cache, préférez `--cache=verify`, qui le jette lui-même au moindre écart. Un `npm ci` le vide aussi.

### Navigateurs suivis

MJS suit les versions récentes de Chrome, Edge, Firefox et Safari. Les navigateurs d'avant 2022 environ ne sont pas suivis : rien n'y est garanti. Une écriture JavaScript qu'un tel navigateur ne connaît pas peut arrêter le script dès sa lecture, et MJS n'y tourne alors pas du tout.

**Cible de compilation : `es2022`.** Un build minifié (`mjs build --prod`, ou `"minify": true`) passe le JavaScript par esbuild avec la cible `es2022` : une écriture plus récente qu'ES2022 y est ramenée à ES2022, celles d'ES2022 et d'avant restent telles quelles (`?.`, `??`, champs de classe…). Aucune cale (*polyfill*) n'est ajoutée : une fonction qui manque au navigateur y manque encore.

**Texte des fichiers : un octet par caractère.** Chrome, comme les navigateurs bâtis sur Chromium, garde en mémoire le texte de chaque script tant que la page vit (Firefox et Safari n'ont pas été mesurés) : sur un octet par caractère si tous tiennent sous U+0100 (l'ASCII, les accents du français, `µ`), sur deux pour tout le fichier dès qu'un seul dépasse (`…`, `’`, `—`, `œ`, `€`, un émoji). Un build de production minifié écrit donc ces caractères-là en échappements (`\u2026`) dans les fichiers JavaScript qu'il émet : le programme reste le même, chaque texte affiché aussi, et le texte gardé est deux fois plus court. Un échappement ne se pose que là où il vaut le caractère : une chaîne, un gabarit sans étiquette, un nom. Un fichier qui porte un tel caractère dans un gabarit étiqueté (`String.raw`), dans une expression régulière ou dans un commentaire sort tel quel, en entier ; pour qu'il en profite, écrivez vous-même l'échappement dans l'expression régulière (`/[\u0300-\u036f]/g`). Un fichier dont le poids monterait de plus de 2 % (un dictionnaire en cyrillique, en grec, en chinois) sort tel quel lui aussi, comme un fichier de plus de 2 Mo de texte (un très gros fichier unique) : l'analyser demanderait trop de mémoire à la construction. Une bibliothèque `.js`, copiée telle quelle, n'est jamais retouchée ; le développement et `"minify": false` ne changent rien non plus. Du code qui lit son propre texte (`fn.toString()`) y voit l'échappement, comme il y voit déjà la minification.

**Les fonctions récentes, testées avant usage.** MJS regarde si le navigateur les a avant de s'en servir ; sans elles, il fait autrement :

| Fonction du navigateur | Avec elle | Sans elle |
|---|---|---|
| API Navigation (`window.navigation`, celle du navigateur seulement : une cale écrite en JavaScript est ignorée) | un écouteur `navigate` de votre page voit passer les pages que sert la navigation de MJS ; deux entrées de l'historique à la même adresse gardent chacune leur position | la navigation de MJS marche de même (liens, formulaires, `Précédent`, `Suivant`), mais ces deux entrées partagent la position de leur adresse — [21 · Navigation](21-navigation.md) |
| couche du dessus (`popover`) | le panneau de `<@@select>`, le menu de `<@@chart>` et la bulle de `:title` passent au-dessus de toute la page | le panneau et le menu s'ouvrent dans leur balise ; la bulle de `:title` est une bulle unique, en `position: fixed` dans `<body>` |
| ancrage CSS (`anchor-name`, `position-area`) | le navigateur les pose contre leur élément | le script les place — [30 · Modules du cœur](30-modules-coeur.md), module par module |
| transitions de vue (`document.startViewTransition`) | les préréglages *pseudo* de `:viewTransition` animent la permutation ; le thème choisi d'un clic s'ouvre en cercle | la permutation se fait directement, sans animation ; le thème s'applique d'un coup — [17 · Router](17-router.md), [31 · Thèmes](31-themes.md) |
| `moveBefore` | `*marquee` déplace un nœud sans le déconnecter : un composant enfant garde son état | `*marquee` le déplace par `insertBefore` |
| `requestIdleCallback` | avec `"messages": "idle"`, le fichier des messages du framework se télécharge page au repos | il se télécharge 200 ms après le chargement de la page |
| `Intl.Segmenter` | un effet qui découpe un texte le coupe caractère par caractère, tel qu'on le lit | il le coupe par point de code : un émoji fait de plusieurs points de code peut s'y couper |

### `urlPrefix`

Préfixe URL public sous lequel les fichiers compilés sont servis (`<script src="{urlPrefix}/bundle.js">`). Absent, il est **dérivé** de `outputDir` (`deriveUrlPrefix`, `src/bundler/index.ts`) selon la convention « la plupart des hébergements servent leur racine documentaire depuis un dossier `public/` » :

| `outputDir` | `urlPrefix` dérivé |
|---|---|
| `public/modularjs` | `/modularjs` |
| `public/assets/X` | `/assets/X` |
| `public` | aucun préfixe (le dossier de sortie est la racine servie) |
| `dist` | `/dist` (convention non respectée, mais accepté quand même) |

Un `outputDir` **absolu** suit la même logique en cherchant `/public/` dans le chemin (ex. `/var/www/monapp/public/modularjs` → `/modularjs`) ; un chemin absolu qui ne contient `public/` nulle part retombe sur son seul nom de dossier final ; un chemin qui finit par `public` (`/var/www/monapp/public`) ne donne aucun préfixe. `"urlPrefix": "/"` (dossier servi à la racine) donne aussi des URL sans préfixe, `/a-<empreinte>.js` — par `mjs.config.json` comme en passant l'option au `Bundler`. Passée au `Bundler`, une adresse d'un autre hôte (un CDN) est publiée telle quelle, sans ses slashs finaux : avec son schéma (`urlPrefix: 'https://cdn.example.com/m'`) comme sans (`'//cdn.example.com/m'`, adresse protocole-relative).

### `stylesheetsDir`

Dossier des feuilles de style **partagées** — celles que l'attribut `:css="nom"` du `<style>` de base va chercher depuis un composant, par opposition au `<style>` scopé d'un `.mjs`, propre à ce seul composant. Défaut `app/modularjs/styles`. Deux feuilles partagées ne portent pas le même nom, quelle que soit leur extension : `a.css` et `a.sass` prendraient toutes deux le nom `a`, une seule serait posée, et la construction le signale par un avertissement qui nomme les deux fichiers.

En `css: "split"` ou `"lazy"`, une feuille nommée `root` (`root.scss`) cohabite avec la feuille racine `mjs_root` : chacune a son fichier.

### `responsiveFontSize`

La taille du texte s'adapte à l'écran sans rien écrire de plus : vous écrivez la taille voulue au PC, en px (`font-size: 41.5px`), et la construction la rend plus petite sur un téléphone. Active par défaut.

Ce que fait la construction : chaque déclaration `font-size` dont la valeur est un nombre en px seul (`!important` gardé), au-dessus du seuil, devient `font-size: var(--mjs-fs-41_5)`. La variable est posée sur `:root` dans la feuille racine, chargée par toutes les pages : sous la largeur de bascule, elle vaut une taille fluide (`calc(1.384375rem + 1.6125vw)`) ; à partir de la bascule, la taille écrite (`2.59375rem`). Une variable par valeur : deux déclarations de même taille partagent la même. Avec les réglages par défaut, `41.5px` vaut 28,4 px sur un écran de 390 px de large, 34,5 px à 768 px et 41,5 px à partir de 1 200 px.

Ce qui est converti : le `<style>` des composants (et leurs déclinaisons `<style name>`), leurs blocs `<theme>` (thème par défaut et thèmes nommés), les fichiers de thème du document (`*.theme.mjs`), les feuilles partagées (`:css`) et la feuille racine `mjs_root`. Ce qui reste tel quel : une taille au seuil ou dessous (rien ne bouge, aucun octet de plus) ; une taille écrite en notation scientifique (`1e2px`) ou avec un signe (`+30px`) ; `rem`, `em`, `%`, les mots-clés, `calc()`, `clamp()`, `min()`, `max()`, `var()` ; le raccourci `font:` ; les feuilles des modules du cœur ; le CSS posé par les effets (`*nom`) pendant l'exécution ; le style écrit sur une balise (`style="…"`, `:style.font-size`) et le `<style>` d'un `<@head>`.

Mettez entre guillemets une adresse `url(data:…)` qui contient du CSS (`url("data:image/svg+xml,…")`) : sans guillemets, un `font-size` en px écrit dedans peut être converti lui aussi, ce qui abîme l'image.

Une taille qui ne doit jamais bouger s'écrit en `rem` (ou en `em`) : `font-size: 2.6rem`.

| Valeur | Effet |
|---|---|
| absente ou `true` | active, réglages par défaut |
| `false` | coupée : le CSS produit est le même, à l'octet, que sans cette fonction |
| un objet | active, avec ces réglages, chacun facultatif |

Réglages : `base` (le seuil, en px, nombre plus grand que 0, défaut `20`), `breakpoint` (la largeur de bascule, en px, nombre plus grand que 0, défaut `1200`), `factor` (la force de la réduction, nombre plus grand que 1, défaut `10`), `unit` (`"rem"` ou `"px"`, défaut `"rem"` ; 1 rem = 16 px).

```json
{ "responsiveFontSize": { "base": 14 } }
```

Avec `"base": 14`, toute taille au-dessus de 14 px s'adapte ; le seuil par défaut, 20 px, laisse le texte courant tel quel.

La sortie en `rem` dépend de la taille de la racine de la page : une règle `html { font-size: … }` qui la change change aussi ces tailles au PC. Dans ce cas, choisissez `"unit": "px"`.

Une valeur fausse (une chaîne, un réglage inconnu, `"base": 0`, `"factor": 1`, `"unit": "em"`…) fait échouer le build avec un message qui la nomme (cf. § *Validation stricte*).

Rendu serveur : la tête que pose le serveur porte le même CSS des tailles que la feuille racine, avant tout script : `mjs_root` converti avec vos réglages, et le bloc `:root` de toutes les tailles de l'appli. La construction écrit ce bloc dans `mjs_ssr_head-font-sizes.css`, à côté du manifeste ; le navigateur ne charge jamais ce fichier. Le fragment d'une page prérendue porte aussi ce bloc, en tête (`<style data-mjs-font-sizes>`), comme le corps d'une page rendue par requête (`createRenderHandler`) : une vue de votre back (Rails…) qui pose ce fragment dans sa propre page, sans la tête du serveur, affiche les bonnes tailles avant le script. En mode `csp`, le fragment lie ce bloc par un `<link rel="stylesheet">` vers un fichier `mjs_ssr_head-….css` du dossier de sortie. Servie par `mjs serve`, la page porte donc le bloc deux fois, dans la tête et dans le fragment, avec les mêmes valeurs. Avec `false`, ni la tête ni le fragment ne changent. `mjs mcp` compile avec la même clé que `mjs build`.

**Limites.** Citez entre guillemets une adresse `url()` qui contient du CSS. Une taille de plus de seize chiffres n'est pas convertie correctement. Ne nommez pas une variable de thème `fs-<nombre>`.

### `manifestExternal`

Le manifeste externe réunit des fichiers par `#= require`, `#= require_dir` et `#= require_tree`, chemins relatifs au fichier qui les écrit. Viser hors de `sourceDir` est permis (un `vendor/` du projet), hors du projet non : un fichier dont le chemin réel (liens suivis) n'est ni sous le dossier de `mjs.config.json` (même quand la commande est lancée d'un sous-dossier du projet), ni sous le dossier parent de `sourceDir`, ni sous le dossier du manifeste arrête la construction, avec une erreur qui nomme la directive et le fichier visé. `require_tree` parcourt chaque dossier réel une fois : un lien vers le dossier lui-même ou vers un parent ne fait pas boucler la construction, et un fichier vu par deux chemins n'est réuni qu'une fois.

### Noms des modules `.civet.mjs` et `.coffee.mjs`

Le nom de fichier d'un module devient son adresse publiée (`<nom>-<empreinte>.js`) : lettres (accents compris), chiffres, `_`, `.` et `-` seulement, et jamais le préfixe `mjs_`, réservé aux fichiers du framework (`mjs_core`…). Un autre nom (`outil#2.civet`, `mon outil.civet`, `mjs_core.civet`) arrête la construction, avec une erreur qui nomme le fichier ; un composant qui l'importe échoue sur la même erreur. Un module ne porte pas non plus le nom d'un composant (`cart.civet.mjs` et `cart.mjs`, même dans deux dossiers) : les deux publieraient le même fichier et le composant ne serait jamais écrit — la construction s'arrête, avec une erreur qui nomme les deux fichiers ; renommez l'un des deux (`cart-logique.civet.mjs`).

### Les dictionnaires `i18n/`

Chaque fichier racine (`i18n/fr.yml`) et chaque dossier de sections (`i18n/fr/`) porte un nom de langue : `fr`, `en`, `pt-BR`, `zh_Hant`, `reel-fr`… (la forme d'une étiquette de langue : un premier sous-libellé de 2 à 8 lettres, puis des lettres et des chiffres après `-` ou `_`). Un nom d'une autre forme (`i18n/__proto__/`, `i18n/mes notes.yml`, `i18n/v1.0.yml`) arrête la construction, avec une erreur qui nomme le chemin. Un fichier de traduction contient un dictionnaire de clés : un YAML vide vaut un dictionnaire vide, un `null` JSON, une liste, un nombre ou un texte seul sont refusés avec le chemin du fichier. Un fragment de section modifié est réécrit au build suivant même quand son nom ne change pas (développement, ou `i18n.hash: false`). Le reste : [29 · i18n](29-i18n.md).

### `assetDirs`

Liste de dossiers d'images **en plus** de `sourceDir` : quand `sourceDir` ne porte pas une image citée par `µimage`, `µasset` (ou ses alias) ou `<@@img>`, le build la cherche dans ces dossiers, dans l'ordre. Chaque chemin est relatif au dossier de `mjs.config.json` et le dossier doit exister ; une valeur qui n'est pas une liste de chaînes, ou un dossier absent, fait refuser la configuration, avec un message qui nomme la clé et la valeur. Défaut : aucune liste, seul `sourceDir` est cherché. Exemple pour Rails, dont le pipeline d'assets garde ses images dans `app/assets/images` :

```json
{
  "sourceDir": "app/assets/modularJS",
  "assetDirs": ["app/assets/images"]
}
```

L'ordre de recherche, le doublon (un même nom dans deux dossiers), le comportement de `mjs dev` et la limite à connaître (une image montrée par une vue Rails ET par un composant sur la même page est téléchargée deux fois) : [35 · Images](35-images.md#des-images-rangées-ailleurs-assetdirs).

### `runtimeDir`

Dossier où trouver le runtime du framework (les fichiers `mjs_*` du cœur), si différent de l'emplacement auto-détecté (`Bundler.locateRuntimeDir`). Un projet qui consomme le paquet npm n'a normalement jamais besoin de le poser : le défaut suit l'installation.

### Le bloc `lint`

Chaque avertissement de compilation appartient à un **type**, et sa ligne se termine par une étiquette `[lint.<type>]`. Cette étiquette dit à la fois ce qui a déclenché la ligne et comment la faire taire : couper un type, c'est poser `"lint": { "<type>": false }` dans `mjs.config.json`. Tous les types valent `true` par défaut — rien ne change tant que rien n'est posé dans `mjs.config.json`. Un avertissement cite la ligne du fichier quand elle est sûre (chaque avertissement `syntax` du HTML en cite une) ; il n'en cite aucune pour une faute venue d'un partiel inclus, ni quand le compilateur a ajouté des lignes au script.

Trois gravités, visibles à la couleur du terminal :

- **erreur** (rouge) — fait échouer le build. Jamais un type de la table ci-dessous, jamais désactivable : seule sa couleur change — sauf `emptyComponent`, qu'on peut changer en erreur (plus bas).
- **avertissement** (jaune) — un défaut probable ou réel de l'application.
- **info** (cyan) — un rappel, sans défaut à corriger.

| type | gravité | ce que ça signale |
|---|---|---|
| `a11y` | avertissement | contrôle d'accessibilité — cf. `lint.a11y` plus bas |
| `ujsForm` | avertissement | `<form>` sans `action` ni méthode — cf. `lint.ujsForm` plus bas |
| `maxStateVars` | info | trop de variables d'état dans un composant du projet (jamais dans un module du cœur) — cf. `lint.maxStateVars` plus bas (reste un entier, `0` coupe) |
| `themeShared` | info | une variable de thème `$$x` déclarée par plusieurs composants — rappel qu'elle cascade, le partage est parfois voulu ; la variable de restylage d'un module du cœur (celle qu'il lit avec sa valeur par défaut, comme `--mjs-number-border` de `<@@number>`) n'en donne pas : la poser dans chaque composant qui l'habille est l'usage prévu |
| `themeUnknown` | avertissement | une variable de thème `$$x` lue mais déclarée nulle part — faute de frappe probable |
| `runtimeHint` | info | un module runtime sélectionné dont le partenaire habituel manque (ex. `ujs` sans `router` : l'interception reste posée mais inerte) ; sans clé `runtime`, les modules optionnels laissés de côté (un module emmené par un autre compte comme gardé), la liste gardée prête à coller, et quoi écrire si une page servie hors construction ou un serveur temps réel qui parle à la page s'en sert ; ou, quand un accès à `µ` ne dit pas quel module sert (`µ[nom]`, `{ ajax } := µ`), que tous sont gardés, le fichier et la ligne de cet accès, et comment l'éviter |
| `runtimeModule` | avertissement | une entrée de `runtime[]` ignorée — nom inconnu, ou préréglage pas encore implémenté |
| `i18n` | avertissement | dossier `i18n/` absent, `i18n.default` sans dictionnaire correspondant, sceau de contrôle d'empreinte manquant ou périmé, traduction en retard sur sa source — [29 · i18n](29-i18n.md) |
| `cssSplit` | info | une feuille de style partagée (`css: 'split'`/`'lazy'`) compilée mais jamais réclamée par un module ni une vue |
| `cssTrap` | avertissement | `@font-face`/`@import` dans le CSS compilé d'un composant — piège Shadow DOM, aucun des deux ne fonctionne dans une feuille construite |
| `collision` | avertissement | deux fichiers distincts publient la même clé de manifeste (basename ou balise) — le second écrase le premier ; deux effets d'une même balise dessinent dans le même pseudo-élément (`::before`, `::after`) — un seul apparaît |
| `tagAlias` | avertissement | un alias `<mjs-nom>` ambigu entre plusieurs sources, une balise de développement inconnue, ou la balise d'un composant du projet écrite sans préfixe (`<nom>` au lieu de `<mjs-nom>` ou `<@nom>`) |
| `animation` | avertissement | une animation citée par `µ.anim.nom` dans un script, que ni la bibliothèque ni un `µanim.create` ne définit — faute de frappe probable ; posée par `:in`, `:out` ou `:transition`, c'est une erreur de construction ([10 · Transitions](10-transitions.md)) |
| `componentFailure` | avertissement | un composant qui échoue à compiler — repêché (dev/serve) ou non (build) |
| `precache` | avertissement | `mjs-precache.json` n'a pas pu être écrit (le build reste valide) |
| `prerender` | avertissement | avertissement du RENDU pendant le prérendu du build (`render.routes` en mode `prerender`) — store non stabilisé, prop invalide… |
| `image` | avertissement | le paquet `sharp` (dépendance optionnelle) est absent : `µimage` garde l'image d'origine, sans variante générée ; ou une image citée existe sous le même nom dans deux des dossiers de `sourceDir` et `assetDirs` (la première de l'ordre de recherche sert) |
| `require` | avertissement | un `#= require`/`require_tree` (manifeste externe) introuvable sur le disque |
| `include` | avertissement | `<@include name>` compilé sans chemin de fichier connu (baseDir absent) : le partial ne peut pas être résolu |
| `routes` | avertissement | le `<script>` d'un composant réassigne `@routes` alors qu'un bloc `<routes>` existe déjà — la table déclarative est remplacée |
| `syntax` | avertissement | HTML du composant mal formé mais récupéré — balise refermée par une autre, jeton de bloc (`{end}`…) en trop, `#{ … }` dans une valeur d'attribut (le `#` s'affiche tel quel) ; une ligne `# …` hors du `<script>` (pas un commentaire : elle s'affiche à l'écran — un commentaire HTML s'écrit `<!-- … -->` ; un `#` seul sur sa ligne, `#1`, un `<pre>`, un `<code>` et un bloc `<@@code>` ne préviennent pas) ; `disabled="false"` et tout attribut booléen écrit à `"false"` (sa seule présence vaut vrai, règle du HTML : retirez-le, ou `disabled={false}`) ; une hauteur nulle ou négative écrite pour `*skeleton` (`height: 0`, `height: -20`), qui ne donne rien à la silhouette ; dans le script, un `µajax` écrit dans un texte que la construction lit comme du code — regex étendue `///…///` sur plusieurs lignes, chaîne écrite dans une interpolation `#{…}`, chaîne sur plusieurs lignes — et qui y devient `µ._mjs_ajax` (cf. [21 · Navigation](21-navigation.md)) |
| `reactivity` | avertissement | réactivité à risque — `µeffect` qui lit et écrit la même variable, cycle entre dérivés, dépendances impossibles à analyser (la vue ne suivra pas), `:this` lié à une variable `$` réactive, une fonction importée d'un module `.js` (copié tel quel) qui écrit directement dans le magasin `$$x` (ou le chemin dedans) qu'elle reçoit en argument — l'écriture change la valeur sans rien redessiner ; une fonction qui ne fait que lire, ou qui passe son paramètre à une autre fonction, n'est pas signalée ([14 · Stores](14-stores.md)) |
| `naming` | avertissement | une variable d'état qui commence par `_mjs_`, préfixe réservé au framework ; `@title = …`, `@id = …`, `@hidden = …`… en tête du `<script>` : c'est une propriété de la balise du composant, pas une donnée (cf. [18 · Pièges](18-pieges.md) § 11) |
| `events` | avertissement | `µemit 'x', e` qui relaie l'événement reçu au lieu de sa charge (le parent lira `e.data` sur le mauvais objet) ; une méthode du composant citée sans `@` dans un gestionnaire (`@click={envoyer}` alors que seul `@envoyer` existe : au clic, rien ne se passerait) |
| `legacy` | avertissement | forme retirée ou dépréciée — `@onUrlChange = ->` (remplacé par la rune `µurlChange`), variable de thème d'un effet fondu dans un autre (`$$shimmer-color` → `$$shine-ink`, cf. [38 · Effets](38-effets.md)) |
| `config` | avertissement | réglage de `mjs.config.json` accepté mais sans effet ou risqué — hôte interne dans `render.forwardOrigin.trustedHosts`, `light` sur une route `csr` |
| `emptyComponent` | avertissement | un composant sans HTML (script ou style seuls, ou un commentaire) : il ne rend rien — `"error"` en fait une erreur de build |
| `unreachable` | avertissement | du code qui suit, dans le même bloc, un `return`, un `throw`, un `break` ou un `continue` : il ne s'exécutera jamais, et la construction de production le retire sans le dire. La ligne citée est celle du fichier source — `<script>`, `<script module>`, gestionnaire en ligne, module `.civet.mjs` ou `.coffee.mjs` importé. Ne sont pas lus : un `<script lang="js">` et les gestionnaires de `<@window>` et de `<@document>`. Une fonction déclarée plus bas (`function nom()`, remontée en tête) et la suite d'un autre bloc (`return if …`, puis le reste) ne sont pas signalées |
| `propUnknown` | avertissement | sur la balise d'un composant du projet (`<@fiche>`, `<mjs-fiche>`), un attribut que ce composant ne lit pas : ni `$titel` dans son script ou son gabarit (un nom à tirets ou en camelCase compte pour la prop qu'il donne : `user-name` et `userName` pour `$userName`), ni l'attribut lui-même (`getAttribute('titel')`, sélecteur `[titel]` ou `attr(titel)` de son style), ni dans ses partiels ni dans les modules qu'il importe, ni chez les modèles d'une base choisis à l'exécution, ni dans ses feuilles de modèle déposées à la main dans le dossier de sortie (`fiche.alt.css`) — la valeur n'arrive nulle part ; le message donne le nom le plus proche (« vouliez-vous écrire « titre » ? »). Ne sont pas signalés : un attribut natif ou global (`class`, `id`, `title`, `hidden`, `slot`…), `data-*`, `aria-*`, une directive (`@click`, `*skeleton`…), `layout`, `template` et `theme` ; `form`, `readonly` et `required` sur un composant `@formAssociated` ; un attribut qu'une feuille du projet vise (`mjs-fiche[titel]`, style du parent ou feuille partagée) ou qu'un script du projet lit par son nom ; la balise d'un module du cœur ou d'une autre bibliothèque ; une balise qui reçoit une propagation `{...obj}` ; un composant qui lit ses attributs d'une façon que la construction ne nomme pas (`getAttribute(nom)`, `$[nom]`, `@attributes`, module chargé depuis une adresse) ([4 · Props](04-props.md)) |
| `routeUnknown` | avertissement | un lien écrit en dur vers une route (`href="#/profil"`, sans `{…}`) qu'aucune route ne prend — paramètres (`:id`, `(:id)`) et joker sous un chemin (`/docs/*`) compris, requête et barre finale retirées comme le fait le routeur : au clic, la page introuvable du routeur ([17 · Router](17-router.md)) ; de même pour un lien que seule une route de repli prend (`/*`, `/(:lang)/*`). Seuls comptent les liens des éléments `<a>` du gabarit ; seulement dans un projet dont toute la table se connaît à la construction (blocs `<routes>`, chemins que le script écrit en toutes lettres sur `@`) : un script, un module ou un gabarit qui nomme `routes` autrement, qui laisse le composant à un autre code (`ajoute(@)`), un module importé qui nomme `routes` ou une construction en échec font taire le contrôle pour tout le projet (jamais un module du cœur, ni le texte d'une chaîne ou d'un commentaire du gabarit, comme `{'@'}` ; une expression régulière n'ouvre ni chaîne ni commentaire ; une forme que le contrôle ne lit pas à coup sûr comme le compilateur, comme une barre qui peut aussi bien diviser qu'en ouvrir une (`{a /b/ c}`) ou une chaîne de plusieurs lignes, fait lire toute la suite du gabarit comme du code) ; un lien vers une autre page (`/doc#/…`), un texte, une chaîne, un commentaire ou un `<textarea>` ne sont pas lus |
| `i18nKeyUnknown` | avertissement | une clé écrite en dur (`µt('panier.vide')`, préfixe de `@i18n` compris, une des sections du module suffit) absente du dictionnaire de la langue par défaut (`i18n.default`, racine ou section) : l'écran montrerait `⟦panier.vide⟧`, en développement comme en production ([29 · i18n](29-i18n.md)) ; le message nomme le fichier à compléter et la clé voisine qui existe. Une clé calculée (`µt("x.#{y}")`), passée par variable ou d'un libellé du framework (`mjs.…`) n'est pas lue |

Exemple — un projet qui a des variables de thème partagées entre plusieurs composants, en connaissance de cause, et qui n'a plus besoin du rappel :

```json
{
  "lint": { "themeShared": false }
}
```

Un composant sans HTML peut faire échouer le build : `emptyComponent` accepte aussi la valeur `"error"`. C'est le seul type qui l'accepte.

```json
{
  "lint": { "emptyComponent": "error" }
}
```

Une clé inconnue dans `lint` (faute de frappe sur un nom de type) fait échouer le build comme toute clé inconnue de `mjs.config.json` — cf. § *Validation stricte*.

**Où les voir.** `mjs build` et `mjs check` finissent par le même bilan, suivi d'une ligne d'aide (« Pour couper un type… ») dès qu'une ligne étiquetée est sortie. `mjs dev` affiche les avertissements imprimés pendant la compilation (accessibilité, syntaxe, réactivité…), et ce bilan une fois, au démarrage ; les recompilations suivantes ne le répètent pas. Le prérendu, qui recompile le projet pour rendre ses pages, ne répète pas non plus ce bilan : il n'écrit que les avertissements de ses rendus (`[lint.prerender]`) et ceux de la compilation que le bilan n'a pas dits, avec leur propre étiquette.

**Couleurs du terminal.** Les lignes ci-dessus sont colorées selon leur gravité (erreur en rouge, avertissement en jaune, info en cyan), l'étiquette `[lint.<type>]` en grisé. `stats.warnings` (consommé par les outils/tests) reste toujours du texte brut, sans couleur : elle ne s'ajoute qu'à l'impression dans le terminal. Mêmes règles que la console de Node : la variable d'environnement `FORCE_COLOR` tranche d'abord — vide, `1`, `2`, `3` ou `true` les allument, toute autre valeur (`0`, `false`) les éteint ; sinon `NO_COLOR` (non vide) et `TERM=dumb` les éteignent ; sinon elles ne s'allument que si la sortie est un vrai terminal — un build redirigé vers un fichier ou un pipe n'en reçoit donc aucune par défaut.

### `lint.maxStateVars`

Plafond d'alerte sur le nombre de variables d'état (`$x`) distinctes déclarées dans **un seul** composant. Défaut réel **40** (`src/transpiler/index.ts`, étalonnage constaté : modules sains 5-20 variables, monolithe pathologique observé à 182). `0` désactive le lint. Au-delà du seuil : un **avertissement** au build, jamais une erreur — un signal d'architecture, rien d'incorrect à l'exécution.

Les modules du cœur (`<@@select>`, `<@@editor>`…, [30 · Modules cœur](30-modules-coeur.md)) n'y sont jamais soumis, quel que soit le seuil : leur nombre de variables est l'affaire du framework, pas de votre application. Une copie éjectée dans vos sources ([30 · Personnaliser](30-modules-coeur.md#personnaliser--trois-leviers-une-règle-de-fair-play)) devient un composant de votre projet : elle est soumise au seuil comme les autres.

### `lint.a11y`

Contrôles d'accessibilité sur le HTML, **activés par défaut** (`true`). Comme le lint précédent : de simples **avertissements** au build, jamais une erreur. Sept contrôles, choisis pour ne parler que quand c'est vraiment un problème :

| ce qui est signalé | pourquoi |
| --- | --- |
| `<img>` sans `alt` sous aucune forme | une image sans alternative est muette pour un lecteur d'écran — `alt=""` est valide et ne dit rien (image décorative) |
| `<iframe>` sans `title` | rien n'annonce ce que contient le cadre |
| `tabindex` positif (`1` et plus) | casse l'ordre de tabulation de la page ; `0` et `-1` sont légitimes |
| `@click` sur `div`, `span`, `li`, `p`, `section`… sans `role` ni `tabindex` | ce qui se clique à la souris ne s'atteint ni au clavier ni au lecteur d'écran |
| `<button>` sans nom accessible | le bouton-icône : rien que du graphique dedans, ni `aria-label`, ni `aria-labelledby`, ni `title` |
| `<a>` sans nom accessible | même cas |
| champ de saisie sans étiquette | `<input>`, `<select>`, `<textarea>` sans `aria-label`/`aria-labelledby`/`title`, et sans `<label>` qui les désigne (son `for` est l'`id` du champ à la lettre près, majuscules comprises : le navigateur ne relie pas `for="Nom"` à `id="nom"`) — le premier champ qu'enveloppe un `<@@field label="…">` au libellé non vide compte comme nommé ; un second champ dans le même `<@@field>` garde son alerte ; un champ hors d'atteinte (`aria-hidden="true"` et un `tabindex` négatif écrits tous les deux sur le champ, comme le champ piège d'un formulaire contre les robots) n'en demande aucune ; les attributs sont lus comme le navigateur les lit (avec ou sans guillemets, `tabindex` comme un nombre entier), et un nom écrit dans la valeur d'un autre attribut ne compte pas |

Deux garde-fous volontaires, pour que le contrôle reste crédible :

- Les blocs `<pre>` sont ignorés entièrement, et les `<code>` ne sont pas inspectés comme du markup — une page qui **montre** du HTML dans ses exemples n'est pas punie pour ça. Le texte d'un `<code>` compte en revanche comme texte visible : `<a href="…"><code>&lt;@view&gt;</code></a>` est un lien correctement nommé.
- Le gabarit est lu par le lecteur du compilateur : les commentaires HTML, le contenu des valeurs d'attributs, les chaînes des expressions `{…}` et le texte d'un `<textarea>` ne sont pas du balisage, et les attributs `{…}` sont lus comme du JavaScript (chaînes, gabarits, regex et commentaires sautés). Un gabarit que la construction refuse (une accolade jamais refermée, par exemple) n'est contrôlé que jusqu'à cette faute. Les avertissements citent la ligne du fichier, même quand le HTML du composant commence après des lignes vides.
- Sur les champs sans `id`, l'alerte ne tombe que si le HTML ne contient aucun `<label>` — un champ enveloppé dans son étiquette ne déclenche rien.

Pour couper : `"lint": { "a11y": false }`.

### `lint.ujsForm`

Avertissement sur un `<form>` qui n'a **ni** `action`, **ni** `:method`/`mjs-method`, **ni** `:noUJS` : le pont UJS l'intercepte quand même — le contrat reste « tout `<form>` est intercepté » — et sans destination déclarée, la soumission repart en navigation vers l'URL courante. `action=""` compte comme absente (même piège que l'absence pure et simple). Un formulaire retenu par `@submit.prevent` n'est pas signalé : le gestionnaire du composant joue avant l'envoi et le retient, le formulaire est local. **Activé par défaut** (`true`), simple **avertissement**, jamais une erreur. Même garde-fou que `lint.a11y` : les `<pre>`/`<code>` d'exemple sont ignorés, les commentaires HTML, le contenu des valeurs d'attributs, les chaînes des expressions `{…}` et le texte d'un `<textarea>` ne sont pas lus comme du balisage, et les attributs `{…}` sont lus comme du JavaScript ; l'avertissement cite la ligne du fichier, même quand il commence par des lignes vides.

Pour couper : `"lint": { "ujsForm": false }`.

### `image`

Politique des variantes produites par `µimage` (cf. [35 · Images](35-images.md)) : `widths` (largeurs à produire, entiers de 1 à 10 000 sans doublon, défaut `[480, 960, 1920]`, jamais au-delà de la largeur native), `formats` (parmi `avif`/`webp`/`jpeg`/`png`, défaut `['webp']`), `quality` (1-100, défaut `78`). Ces variantes exigent `sharp`, dépendance **optionnelle** (`npm i -D sharp`) — absente, l'image d'origine passe telle quelle et un avertissement unique le dit ; les **dimensions natives**, elles, sont toujours lues (en-tête du fichier, aucune dépendance) et ne dépendent pas de ce bloc.

```json
{
  "image": { "widths": [320, 640, 1280], "formats": ["avif", "webp"], "quality": 80 }
}
```

### Ce que porte le manifeste

Le fichier `manifestPath` est servi sur **chaque** page : tout ce qu'il embarque est payé à chaque
visite. Il porte donc la table des composants et les réglages, jamais la prose du site.

- **Table des chemins** — `µ.paths`, un nom logique par composant/module. Les valeurs partagent
  toutes le même début d'URL (`urlPrefix`) : ce préfixe est publié **une seule fois**
  (`µ.pathsPrefix`) et chaque valeur ne garde que son suffixe (`about-<empreinte>.js`) ; qui lit un
  chemin recolle les deux. Sur un site à ~1 400 composants, c'est 37 Ko de préfixe recopié en moins
  sur chaque page. En production, à partir de 40 entrées, la valeur est réduite à ce que la clé ne dit
  pas déjà : l'empreinte seule (`"about":"k3x9a"`), ou le préfixe de dossier suivi de l'empreinte
  (`"ajax":"tuto-m81pz"`) ; un nom de fichier entier (fichier de groupe ou de page) garde son
  point. Aucun fichier n'est renommé. Pour obtenir le chemin entier d'un nom, lisez `µ.pathOf(nom)`
  (chaîne vide si le nom est inconnu) plutôt que `µ.paths[nom]`. En développement et sous 40 entrées,
  la table reste entière. En `js: 'bundle'`, la forme ne change pas (chaque nom pointe le fichier unique).
- **Réglages** — préchargement (`preload`), niveau de journal, libellés du framework, thèmes.
- **i18n** — les **réglages** seulement (langue par défaut, mode placeholder, détection…), plus la
  liste des langues et l'URL du **fichier de chaque langue** ; dictionnaires et table des sections
  vivent dans ces fichiers, chargés pour la seule langue affichée — cf.
  [29 · i18n](29-i18n.md) §2.

Conséquence pratique : le manifeste ne **porte** plus la prose du site (site de référence : 142 Ko
bruts, 33 Ko gzip de moins par page servie), et un visiteur ne télécharge que la langue affichée —
plus la langue par défaut si elle diffère, qui porte les replis. Ce fichier se paie **une** fois :
sur la première page le solde est de −16,6 Ko gzip en français et à peu près nul en anglais (deux
fichiers) ; dès la deuxième page il vient du cache et le gain est plein. Changer une **traduction**
change le fichier de sa langue **et** l'empreinte que le manifeste en garde : le manifeste change
donc encore, comme à chaque construction ; les fichiers des autres langues et le JavaScript des
composants, eux, ne bougent pas.

### `js`

Par défaut (`"js": "split"`, ou la clé absente), chaque composant, chaque module `.civet.mjs`/`.coffee.mjs` et le cœur du runtime deviennent leur propre fichier haché (`mjs_core-<empreinte>.js`, `mon-composant-<empreinte>.js`…) dans `outputDir` ; l'empreinte tient en 5 caractères (`0-9a-z`, tirés du contenu du fichier) : une chance sur 60 millions par fichier modifié que deux contenus partagent un nom, compromis assumé contre des noms plus courts (environ 2 Ko de moins sur un site réel) ; deux contenus qui recevraient le même nom font échouer le build, jamais un fichier écrasé sans bruit, et le manifeste (`manifestPath`) se contente de les orchestrer — un `import()` dynamique par unité, chargée quand sa balise apparaît dans la page (`µ.Autoloader`). Sur un site à nombreux composants répartis sur plusieurs pages, c'est ce qui permet à une page de ne charger QUE ce qu'elle affiche.

Une page bâtie dans le navigateur n'attend pas les composants que nomme son gabarit : elle se dessine dès que son propre fichier est là, et chaque composant paraît à l'arrivée du sien (une page rendue par le serveur, elle, attend les fichiers de ses composants, une demi-seconde au plus, avant de les reprendre en main d'un seul geste : [Rendu serveur](19-ssr.md)). Pour que ce qui suit un composant ne bouge pas à ce moment-là, donnez sa place à sa balise : `<@carte :size="320x48">` la garde vide, `<@carte :size="320x48" *skeleton>` y dessine la silhouette grise ([Composant](02-composant.md)).

Tant que le fichier d'un composant n'est pas arrivé, puis jusqu'à son premier rendu, sa balise est **invisible** (`visibility: hidden`, jamais `display: none`) : rien ne se peint, rien ne se clique, rien ne prend le focus, rien n'est lu par un lecteur d'écran. Elle garde la place que vous lui donnez avec `:size` ; sans lui, elle n'en a aucune, et ce qui la suit descend quand il paraît. Il paraît d'un coup, sans qu'aucune transition de sa feuille ne se joue pendant l'attente ni à son apparition : ce que son premier rendu et son `µmount` changent (une classe, un effet comme `*filter`, l'état coché d'une case) est déjà en place à la première image où il se voit, ses pseudo-éléments (`::before`, `::after`) compris quand il a attendu ses textes, sa feuille ou un composant qui le contient (la coche d'un interrupteur, par exemple), et un élément en `transition: opacity .3s, visibility 0s .3s` paraît avec lui, sans attendre son délai, même dans une page qui n'affiche encore rien d'autre, de même que le contenu que la page glisse dans sa balise et celui qu'un composant lui transmet par son propre `<slot>`. Ses transitions reprennent dès qu'il paraît, pour tout ce qui change ensuite : une animation d'entrée se lance depuis `µmount` dans un `requestAnimationFrame` (une classe posée sur un élément de son gabarit ou sur sa balise), alors qu'une classe posée directement dans `µmount` est déjà en place quand il paraît (sous Firefox, et parfois sous Chromium quand l'appli tient en un seul fichier (`"js": "bundle"`), la même classe posée sur la balise d'un composant placé dans la page, hors d'un autre composant, part en fondu). Une limite : un `µmount` qui lit la mise en page (`offsetWidth`, `getBoundingClientRect()`, `getComputedStyle()`…) puis change un style fait partir ce changement en transition à l'apparition, ses pseudo-éléments compris, comme sur une balise déjà affichée : sa lecture a fait calculer au navigateur l'état d'avant. Couper ces transitions-là coûterait une passe de style de plus pour tout le contenu de chaque composant à `µmount`, à chaque apparition (4 ms pour 400 composants dans Chromium) ; changez le style avant de mesurer, ou coupez vous-même la transition de l'élément le temps de ce changement (une classe en `transition: none`, retirée dans un `requestAnimationFrame`). De même, une balise déjà affichée dans une page peinte quand son code arrive avec le cœur (fichier unique, `"js": "bundle"`) n'a jamais été cachée : ce que la feuille du composant change sur elle-même (`:host`) se joue en transition, comme sur toute balise affichée. Rien n'attend d'image : dans un onglet en arrière-plan, il paraît et ses transitions reprennent de même ; le navigateur y espaçant ses minuteries, la balise d'un composant dont le fichier arrive après la page y paraît environ 0,3 s plus tard qu'au premier plan (pour un fichier servi en 300 ms : 616 ms dans Chromium et 641 ms dans Firefox, contre 312 et 318 ms). Un composant placé dans un autre qui attend encore (dans sa balise, dans son gabarit, ou transmis par un `<slot>` au composant qui attend) paraît à la même image que lui, dans l'état où l'attente l'a laissé : une animation d'entrée qu'il a lancée pendant l'attente ne se joue pas. Une limite, sous Firefox et WebKit : le contenu que vous glissez dans un composant, et que celui-ci transmet par son propre `<slot>` à un composant dont le fichier arrive après la page (`"js": "split"`), paraît avec l'animation qu'il a lancée depuis `µmount` dans un `requestAnimationFrame` déjà entamée (une couleur en fondu d'une seconde y est aux deux tiers à la première image où il se voit). Les éléments nommés de la page n'y changent rien : un `<form name="host">`, une `<img name="parentNode">` ou un `<object id="host">`, qui recouvrent la propriété du même nom de `document`, pas plus qu'un champ `name="parentNode"` dans un formulaire. Un composant rendu par le serveur, déjà affiché, est repris sans cette coupure quand il paraît dans la foulée ; il la reçoit quand son apparition attend (sa feuille, ses textes, un composant qui le contient et qui est encore caché). Cela vaut pour tout ce que la balise contient, même un élément qui se déclare visible (`visibility: visible`, la classe `visible` de Tailwind ou de Bootstrap) : il reste caché avec elle. Seules les balises que le chargeur va chercher sont concernées, celles des composants de votre projet (le manifeste) : la balise d'une autre bibliothèque (`<autre-lib>`, définie plus tard par elle ou jamais) n'est jamais touchée, et une balise `mjs-*` mal écrite s'affiche telle qu'elle est écrite, son contenu compris, pendant que l'autoloader la dit absente du manifeste en console (« Rejet : Composant '…' absent du manifeste de distribution »). La place gardée est celle de ce que la balise contient déjà (texte, blocs écrits entre ses balises), et celle que votre feuille lui donne : une balise vide, `<mjs-carte></mjs-carte>` ou `<@@number>`, n'a pas de taille tant que son composant n'est pas là — réservez-la dans le CSS de la page (`mjs-carte { display: block; min-height: 12rem }`), elle tient pendant l'attente.

`"js": "bundle"` change cette stratégie du tout au tout : le cœur, les feuilles partagées, les animations utilisées, le manifeste externe, les modules et TOUS les composants du projet sont assemblés dans le seul fichier `manifestPath` — plus aucun autre `.js` dans `outputDir`, sauf, en production, le chargeur des messages de la console (ci-dessous), et ce que charge `µimport` : un `.js` cité, ou un module MJS chargé à la demande (lui et les modules que seuls des modules chargés à la demande importent ne sont téléchargés et évalués qu'à l'appel) avec le fichier du code qu'il partage avec le reste (le cœur, un module importé des deux côtés), que le fichier unique importe dès le démarrage (les satellites CSS de variants et les images restent des fichiers, inchangés). Ces fichiers sont écrits **à côté de `manifestPath`**, dans `outputDir` ou, si le manifeste est ailleurs, dans le dossier du manifeste : le fichier unique les cite par un chemin relatif, qui se lit depuis son adresse. Hors d'`outputDir`, ils ne figurent pas dans `mjs-precache.json`, dont les adresses se déduisent d'`urlPrefix` : le build ne connaît pas l'adresse publique du manifeste. Le build les consigne dans le registre `.mjs-outputs.json`, à côté du manifeste, et ne retire jamais que ceux-là. Une page ne fait plus qu'une seule requête JavaScript au démarrage (deux quand un module MJS est chargé à la demande), tout est chargé et défini d'un coup, `µ.Autoloader` n'a plus rien à découvrir puisque rien n'arrive plus tard. Seule exception, en production : le premier message écrit dans la console télécharge le chargeur des messages, `mjs_msg-<empreinte>.js`, écrit dans `outputDir` et absent de `mjs-precache.json`, comme dans un build éclaté ([29 · i18n](29-i18n.md)) ; une page où aucun message ne s'écrit ne le demande jamais. C'est le choix pertinent pour une petite application ou une page unique où « tout charger tout de suite » coûte moins qu'une cascade de petites requêtes — pas pour un site qui étale ses composants sur de nombreuses pages, où ce serait l'inverse (chaque page paierait le poids de composants qu'elle n'affiche jamais).

Trois choses à savoir :

- **Le mode exige `css: 'bundle'`** (le défaut). C'est mécanique, à l'envers du raisonnement de `csp` ci-dessous : fusionner en un seul fichier un CSS déjà DÉCOUPÉ en fichiers séparés (`"css": "split"` ou `"css": "lazy"`) contredirait « un seul fichier JS ». Avec l'un de ces deux réglages, le build refuse de partir et le message nomme le correctif.
- **Incompatible avec `csp: true`** : le mode strict exige justement un CSS découpé (cf. `csp` plus bas), l'inverse de ce que `js: 'bundle'` impose — aucune valeur de `css` ne peut jamais satisfaire les deux à la fois, un message dédié le dit avant même de parler de `css`.
- **L'Autoloader n'est pas embarqué** : tout composant est défini dès le chargement du fichier unique, il n'a plus rien à découvrir. Un contrôle unique, après la définition de tous les composants, signale en console toute balise `mjs-…` présente dans la page et inconnue du projet (une faute de frappe, ou un web component tiers voulu). `"runtime": ["autoloader"]` le remet si un projet en a besoin.
- **Le rendu serveur et le rendu navigateur restent TOUJOURS en `'split'`**, quel que soit ce réglage : ils rechargent le cœur et chaque composant fichier par fichier pour leurs propres besoins internes (prérendu, tests Chromium). Sous `js: 'bundle'`, cette recompilation de service écrit dans un **dossier temporaire à elle**, retiré aussitôt : `outputDir` et son fichier unique sortent du prérendu intacts, à l'octet près. Les URLs d'assets du HTML rendu (images `µasset`, feuilles, liens) restent celles du vrai build — ce détail d'implémentation ne change jamais ce qu'un visiteur reçoit.

```json
{
  "js": "bundle"
}
```

> **Changer de mode purge peu.** Passer de `'split'` à `'bundle'` (ou l'inverse) sur un `outputDir` déjà construit laisse les anciennes sorties de l'AUTRE mode sur place (les `mjs_core-*.js`/`<composant>-*.js` d'un ancien `'split'` ne sont jamais reconnus comme orphelins par un build en `'bundle'`, qui n'écrit plus rien de tel) : `prune` ne les retire pas. Videz `outputDir` à la main après un changement de mode.

### `csp`

Certains hébergements — banque, santé, secteur public, ou simple politique interne — imposent une **politique de sécurité de contenu** stricte : l'en-tête `Content-Security-Policy` y interdit tout style et tout script écrits *en ligne* dans la page, du genre `script-src 'self'; style-src 'self'` sans la moindre échappatoire `'unsafe-inline'`. Le navigateur refuse alors purement et simplement d'exécuter un `<script>` sans `src`, et d'appliquer un `<style>` posé dans le HTML.

`"csp": true` met MJS en conformité avec une telle politique : à partir de là, **rien de ce que MJS écrit ne serait refusé**. Le CSS du thème part en fichier avec empreinte et arrive par un `<link>` ; les feuilles de composant rendues au serveur passent elles aussi par un `<link>`, à l'intérieur du shadow root — pour **chaque** composant du HTML rendu, racine comme sous-composant, à ombre comme léger ; le drapeau d'hydratation devient un attribut au lieu d'un script ; et les quelques endroits où le runtime fabriquait une balise `<style>` à la volée adoptent une feuille de style construite en mémoire, que la politique ne regarde pas.

Trois choses à savoir :

- **MJS n'impose aucune politique.** Il n'émet jamais d'en-tête `Content-Security-Policy` lui-même : écrire cet en-tête reste l'affaire de l'application ou du serveur de façade. La clé rend MJS *compatible*, elle ne décide rien à votre place.
- **Le mode exige un CSS découpé** (`"css": "split"` ou `"css": "lazy"`). C'est mécanique : remplacer un `<style>` en ligne par un `<link>` suppose qu'un fichier existe à pointer. Avec `"css": "bundle"`, le build refuse de partir et le message nomme le correctif — et donc, transitivement, `"csp": true` est aussi incompatible avec `"js": "bundle"` (cf. `js` plus haut), qui exige justement `css: 'bundle'`.
- **`mjs serve` et `mjs dev` les servent au préfixe DÉRIVÉ.** Ces feuilles sont référencées par leur URL publique, celle que le projet déclare dans `urlPrefix` ou, à défaut, celle que MJS dérive du dossier de sortie (`public/modularjs` → `/modularjs`, cf. [`urlPrefix`](#urlprefix)) — même règle côté écriture et côté service, donc rien à accorder à la main. Ne déclarez `urlPrefix` que si votre back monte le dossier ailleurs que ne le dit cette convention.
- **Les feuilles écrites par le rendu ne sont jamais purgées.** Celles-là (`mjs_ssr_style…`, `mjs_ssr_head…`) naissent au prérendu, pas à la compilation : `prune` les épargne par leur nom, sans quoi le build les retirerait aussitôt écrites et les `<link>` des fragments pointeraient dans le vide. En contrepartie, la feuille d'un composant **supprimé du projet** reste sur disque, orpheline — elle n'est plus référencée par aucun fragment, son nom porte l'empreinte de son contenu, elle ne peut donc rien écraser ni rien servir de faux. Videz `outputDir` à la main quand ce résidu vous gêne.
- **Le défaut reste `false`**, et le chemin par défaut ne change pas d'un octet. Ce n'est pas de la prudence de façade : une feuille adoptée en mémoire passe *après* les `<style>` et les `<link>` du document dans l'ordre de cascade. Basculer tout le monde changerait donc qui gagne un conflit de règles, et pourrait casser une surcharge d'application qui marche très bien aujourd'hui. Sans la clé, le cœur ne porte pas la voie des feuilles construites des composants légers (`mjs-light`), qui gardent leur `<style>`.

```json
{
  "csp": true,
  "css": "split"
}
```

#### Trusted Types : `require-trusted-types-for 'script'`

La politique la plus stricte ajoute `require-trusted-types-for 'script'` à l'en-tête. Le navigateur refuse alors toute écriture de HTML faite à partir d'une simple chaîne (`innerHTML`, `DOMParser`…), même vide : seule passe une valeur de confiance, fabriquée par une **politique** nommée (Chrome et Edge, Firefox 148 et plus, Safari 26 et plus). Une appli MJS tourne sous cet en-tête sans aucun réglage : il ne dépend pas de la clé `csp`.

- **Le HTML que MJS fabrique lui-même passe par sa politique `mjs`** : le gabarit compilé de chaque composant (`{if}`, `{for}`, `{await}` compris), les morceaux des effets et de la modale, `<@head>` et `<@failed>` quand leurs valeurs sont échappées, le HTML qu'un module du cœur a lui-même normalisé (la surface de `<@@editor>`, ce qu'il colle, dépose ou insère comme lien, toujours réécrit par son nettoyeur, les icônes de `<@@toolbar>`), le panneau de développement, et la page suivante lue par la navigation du framework : la réponse de votre serveur, la même confiance qu'une page chargée en entier. La politique est créée au premier gabarit, seulement là où le navigateur connaît Trusted Types. Les vidages passent par `textContent`.
- **Le HTML d'auteur n'y passe jamais** : `{{…}}`, `:html=!{…}`, `:title={{…}}`, l'option `html` de `µ.modal.fire()`, un `{{…}}` écrit dans `<@head>` ou `<@failed>`, un repli `@failed` qui rend une chaîne. Le confier à la politique `mjs` laisserait entrer n'importe quelle donnée. Sous l'en-tête strict, il passe par la politique `default` de votre page quand elle existe, et c'est à elle d'assainir ; sinon le navigateur le refuse. Pour `{{…}}` et `:html`, le contenu reste alors vide, le reste du composant s'affiche et la console dit quoi faire ; ailleurs, c'est l'erreur du navigateur qui s'affiche.
- **Une valeur TrustedHTML de votre propre politique** est acceptée telle quelle par l'option `html` de `µ.modal.fire()` ; `{{…}}` et `:html` la lisent comme du texte, si bien que seule la politique `default` compte pour eux.
- **Une page qui liste ses politiques** (directive `trusted-types`) doit y nommer `mjs`, à côté de `default` si elle en pose une. Sans `mjs` dans la liste (ou avec `'none'`), le navigateur refuse de créer la politique du framework : MJS écrit alors son HTML en simple chaîne, comme dans un navigateur sans Trusted Types, et un avertissement de la console, écrit une seule fois, dit d'ajouter `mjs`. Une page qui liste ses politiques sans exiger Trusted Types (sans `require-trusted-types-for`) se monte donc normalement ; Chrome, Firefox et WebKit relèvent pourtant, à chaque chargement, la création refusée comme une violation de la politique de sécurité (événement `securitypolicyviolation`), et Chrome et WebKit l'envoient à l'adresse `report-uri` de l'en-tête quand elle y est écrite (Firefox ne l'envoie pas). Sous l'en-tête strict, ces chaînes passent par la politique `default` de la page quand elle existe, qui peut les modifier ; sans elle, le navigateur les refuse et aucun composant ne se monte. Une politique `mjs` déjà créée par un autre script de la page a le même effet : si deux scripts de la page la créent, ajoutez `'allow-duplicates'` à la liste.

```http
Content-Security-Policy: require-trusted-types-for 'script'; trusted-types mjs default
```

```js
// posée avant le script de l'appli : assainit tout HTML d'auteur qui arrive sans valeur de confiance
trustedTypes.createPolicy('default', {
  createHTML: (html) => DOMPurify.sanitize(html)
})
```

### `sourceMap`

Une **carte de source** est le petit fichier `.map` qui relie le JavaScript livré au navigateur au fichier que vous avez écrit. Sans elle, un point d'arrêt tombe au milieu du code compilé ; avec elle, il tombe sur *votre* ligne, dans *votre* `.mjs`.

| Valeur | Émission |
|---|---|
| `'dev'` | en développement seulement — le défaut |
| `'prod'` | en build de production seulement |
| `'always'` | dans les deux |
| `'never'` | jamais |

Le défaut `'dev'` découle directement de là : la carte est émise là où elle sert — pendant que vous développez — et absente de la production, où elle publierait la forme lisible de votre code à qui ouvre les outils du navigateur. `'prod'` rétablit le comportement des versions précédentes.

> **Ce que la carte couvre.** Le `<script>` de votre composant, ligne par ligne : le navigateur vous affiche votre `.mjs` d'origine — Civet, Coffee ou TypeScript — et non le JavaScript assemblé, y compris sur un fichier minifié. Le source du `.mjs` est embarqué dans la carte, il n'a donc pas besoin d'être servi. Restent en dehors : le bloc `<script module>` (code de module, hors de la classe du composant) et les gestionnaires écrits directement dans le HTML (`@click={…}`), assemblés à part.

### `prune`

Le build remplace déjà l'empreinte d'un fichier qui **change** — `cleanupOldHashes` retire l'ancienne version une fois le nouveau manifeste publié. Un nom qui **disparaît** (composant renommé ou supprimé) est un cas différent : personne ne le retire, son fichier reste dans `outputDir` indéfiniment.

Rien ne le sert — le manifeste ne le référence plus — mais sa seule présence fait mentir le dossier sur ce que le site contient réellement : c'est ce qu'on relit six mois plus tard en se demandant pourquoi `outputDir` pèse dix fois ce que le dernier build a écrit.

Après un build **sans erreur** (jamais après un build partiel — cf. § *Validation stricte* ci-dessous), avant le prérendu, `mjs build` retire donc d'`outputDir` les fichiers qu'un build a écrits (`nom-<empreinte>.ext`, son `.map`, une variante d'image, la feuille `<composant>.<nom>.css` d'une déclinaison `<style name>`) et qu'il n'a pas produits ce tour-ci. Il le sait par le registre `.mjs-outputs.json`, à côté du manifeste, qui garde la liste des fichiers écrits par les builds (clé `files`, et `layoutStyles` pour ces feuilles).

> ℹ️ **Un dossier de sortie construit par la 2.5.0** n'est pas rangé après coup : la 2.5.0 ne notait pas les fichiers qu'elle écrivait, ils manquent donc au registre et la purge les laisse en place. Retirez-les une fois à la main (les `nom-<empreinte>.ext` et leurs `.map`), ou construisez dans un dossier vide ; ensuite, chaque build retire ce qu'un build précédent a écrit et qu'il ne produit plus.

**Jamais un fichier sur la seule forme de son nom.** Un fichier à vous posé dans le dossier de sortie — `card-utils.js` à côté d'un composant `card.mjs`, `logo-white.png` à côté d'une image `logo.png`, `theme-light.css`, `vendor-0123abcd.js` — n'est jamais retiré : ni par cette purge, ni quand le build remplace l'empreinte d'une de ses propres sorties. Le dossier de sortie peut même être le dossier source (ou un dossier dedans) : aucun fichier source n'est retiré ni réécrit. Les sorties à nom fixe — le manifeste, la feuille `<module>.<nom>.css` d'un `<style name="…">`, `mjs-precache.json` — y portent alors une marque : la première ligne `/* @generated by ModularJS */` pour le manifeste et les feuilles, la clé `"@generated": "ModularJS"` pour `mjs-precache.json` (à côté de `version` et `assets`, inchangés). Les autres sorties JSON à nom fixe — le registre `.mjs-theme-vars.json` (développement), les noms courts `.mangle-cache.json` (production), la carte `<manifeste>.map` du fichier unique, les fragments de traduction à nom clair `i18n/<langue>/<section>.json` — ne portent pas de clé de marque (le registre et les fragments la liraient comme une donnée) : elles sont reconnues à leur forme, la même depuis la 2.5.0, et un fichier à vous du même nom, d'une autre forme, est refusé de la même façon. Elles ne remplacent qu'un fichier qui porte cette marque : un fichier à vous du même nom arrête la construction avant toute écriture, par une seule erreur qui nomme tous les fichiers en cause, et reste intact. La preuve est dans le fichier même : un clone sans registre `.mjs-outputs.json`, un registre perdu ou un manifeste déplacé n'y changent rien. Après la mise à jour depuis la 2.5.0, son manifeste et son `mjs-precache.json` sont reconnus et réécrits ; ses feuilles `<module>.<nom>.css`, qui n'ont aucun signe sûr, sont refusées une fois, toutes dans la même erreur : supprimez-les puis relancez. Hors du dossier des sources, les sorties ne portent aucune marque. Un projet traduit fait exception : les fragments de traduction iraient dans `i18n/<langue>/`, le dossier même de vos traductions — le build le refuse par une erreur, avant d'écrire quoi que ce soit ; donnez alors à `outputDir` un dossier distinct. En contrepartie, un dossier de sortie laissé par une version qui ne tenait pas cette liste (la 2.5.0) n'est pas rangé rétroactivement : ses anciennes sorties restent, videz `outputDir` à la main une fois après la mise à jour ; seuls les fichiers écrits depuis par le build sont suivis.

En `"js": "bundle"`, le build ne se fie jamais à la forme d'un nom : il retire les fichiers écrits à côté du manifeste (module chargé à la demande, code partagé) que le registre dit écrits par un build et que ce build n'a pas réécrits — un module retiré ou renommé laisse donc ses fichiers jusqu'à ce `mjs build`, et un fichier à vous nommé `chunk-deadbeef.js`, posé à côté du manifeste, n'est jamais touché, que le manifeste soit dans `outputDir` ou ailleurs. Avec `"prune": false`, ces fichiers restent.

Chaque retrait est annoncé, jamais silencieux : `🧹 8 fichiers orphelins retirés de public/modularjs`, suivi du nom de chacun (vingt au plus, puis `+ N autres`).

Jamais touchés : les sous-dossiers de `outputDir` (hors les fragments de traduction, voir plus bas) et les pages de `render.outDir`, le manifeste, les feuilles `.css` de layout déposées à la main, les fichiers de travail du bundler (`.mangle-cache.json`…), tout fichier que le registre `.mjs-outputs.json` ne liste pas, et toute extension absente de ce registre (un `.pdf`/`.zip` posé à la main, par exemple). Une feuille `<composant>.<nom>.css` que le build écrit pour une déclinaison `<style name>` part, elle, quand la déclinaison quitte les sources ; une feuille de layout que vous déposez n'est jamais retirée, même sous le nom d'une feuille que le build avait écrite : le registre note l'empreinte de chaque feuille qu'il écrit, et une feuille au contenu changé n'est plus la sienne (seule une copie identique à l'octet à la sienne part avec la déclinaison).

**Les fragments de traduction** (`i18n/<langue>/*.json`) suivent la même règle, avec une précision : le build ne retire que les fichiers **qu'il a écrits lui-même** et qu'il n'a pas réécrits ce tour-ci (un texte modifié en production donne un nouveau nom, l'ancien fragment n'est plus servi ; une section supprimée ou une langue retirée des sources laisse le sien). Il le sait parce que le registre `.mjs-outputs.json` garde la liste des fragments écrits, langue par langue — jamais d'après la forme du nom : un `.json` que vous posez dans `i18n/<langue>/` (`notes.json`, un nom qui ressemble à une empreinte, le nom d'une section) n'est jamais retiré. Avec `"prune": false`, aucun fragment n'est retiré : les anciens restent à disposition des onglets restés ouverts. Un dossier de fragments laissé par une version qui les vidait à chaque build n'est pas rangé rétroactivement : seuls les fragments écrits depuis par le build sont suivis.

`"prune": false` désactive la purge, et aussi le retrait de l'ancienne empreinte d'un fichier qui change — le dossier accumule alors comme avant. `mjs dev` et `mjs serve` ne la déclenchent jamais : seul `mjs build` le fait.

À savoir : un onglet resté ouvert sur un build précédent peut perdre ses imports différés au rechargement, les empreintes changeant à chaque déploiement. Garder les anciens fichiers à disposition le temps qu'un onglet oublié se recharge, c'est `"prune": false`.

**`.mangle-cache.json`** (à côté des sorties, en production) garde les noms courts donnés aux propriétés internes, pour que deux builds du même code donnent les mêmes fichiers. Il peut être versionné. Relu à chaque build, il est contrôlé : une valeur qui n'est pas un texte, ou un même nom court donné à deux propriétés (ce que peut laisser une fusion git), est écartée avec un avertissement et recalculée — jamais transmise au minifieur. Un cache laissé en conflit par une fusion git (lignes `<<<<<<<`, `=======`, `>>>>>>>`) est recalculé en entier. Quand les sorties sont dans le dossier des sources, un cache abîmé de ces façons reste reconnu à ses clés (propriétés `_mjs_…`, noms réservés à `false`) et il est remplacé ; seul un fichier de ce nom qui n'a pas cette forme est refusé.

Le nom seul ne suffit pas à reconnaître une sortie du bundler : un fichier étranger déposé à la main peut, par pure coïncidence, prendre la forme `nom-<empreinte>.ext` (ex. `rapport-1a2b3c4d.pdf`) sans jamais avoir été écrit par un build — d'où la liste des fichiers écrits, ci-dessus. Un second filtre porte sur l'**extension** : à côté du manifeste, un registre `.mjs-outputs.json` liste les extensions que ce bundler a produites (`.js`/`.css`/`.map` toujours, les formats d'image configurés, plus toute extension effectivement rencontrée) — seul un fichier dont l'extension y figure est candidat à la purge. Registre absent : base minimale `.js`/`.css`/`.map` + formats d'image configurés. Registre présent mais illisible (JSON corrompu ou de forme inattendue) : la purge entière est sautée, aucun fichier retiré — mieux vaut ne rien purger que deviner sur un registre douteux.

### `bundles`

Une page qui contient des dizaines de petits composants (un onglet et ses cartes, par exemple) les charge un par un : autant de requêtes que de fichiers. `bundles` en fait un seul fichier par groupe.

```json
{
  "bundles": {
    "onglet-texte": ["fx-famille-text"],
    "onglet-fond":  ["fx-famille-background", "fx-famille-border"]
  }
}
```

Chaque clé est le nom d'un groupe (lettres minuscules, chiffres et tirets) ; sa valeur liste ses composants **racines**, par leur nom de fichier, avec ou sans le préfixe `mjs-`. En production (`--prod`), un groupe assemble ses racines **et toute leur descendance** — les composants que leurs gabarits écrivent, de proche en proche — dans `mjs_group-<nom>-<empreinte>.js`. Le manifeste fait pointer chaque composant du groupe vers ce fichier : charger l'un d'eux charge le groupe entier, une seule fois.

Pour laisser certains composants **dehors**, un groupe prend la forme objet :

```json
{
  "bundles": {
    "onglet-composants": { "roots": ["onglet-composants"], "except": ["core-field", "core-gauge", "core-tabs"] }
  }
}
```

Un composant listé dans `except`, **et la descendance qu'il est seul à atteindre**, restent en fichiers séparés : ils se chargent comme d'habitude quand la coquille du groupe les appelle, et une page qui n'utilise que l'un d'eux ne télécharge pas le groupe. Ils restent dans la table des dépendances : `µ.Autoloader.preload` de la racine les charge d'avance avec le groupe. `roots` est la liste que la forme courte donne directement ; `except` est facultatif, et `{ "roots": [...] }` seul équivaut à la forme courte.

Restent des fichiers à part, jamais recopiés dans le groupe : le cœur, les **modules** (`.civet.mjs`/`.coffee.mjs`, qui doivent rester une instance unique), les feuilles partagées, les animations, les fichiers de langue et les fichiers d'effets. Les fichiers séparés de chaque composant sont toujours écrits : le rendu serveur les lit un par un, et `prune` ne les retire pas. En développement, rien n'est regroupé — une ligne au journal du build le dit.

- **Un composant ne peut appartenir qu'à un seul groupe.** Un composant atteint par plusieurs groupes arrête le build, et l'erreur les relève **tous d'un coup** : pour chaque composant, les groupes qui l'atteignent (au-delà de trois, les deux premiers puis « … »), puis ce qu'il faut écrire pour les sortir de ces groupes : la ligne `"except"` exacte à ajouter aux groupes, et la liste complétée de chaque groupe qui a **déjà** un `except` — à écrire à la place de l'ancienne, car un second `"except"` dans le même groupe remplacerait le premier en silence. Un groupe écrit en liste prend la forme objet (`["racine"]` devient `{ "roots": ["racine"], "except": [...] }`), ce que le message rappelle quand l'un des groupes à modifier est une liste. Suivie à la lettre, la consigne fait passer la construction : pas de second tour.

  ```
     [bundler] ✗ 3 composants sont dans plusieurs groupes : core-checkbox, core-option, core-select
     core-checkbox : 3 groupes : onglet-carte, onglet-fond, onglet-texte
     core-option : 2 groupes : onglet-carte, onglet-texte
     core-select : 2 groupes : onglet-carte, onglet-texte
     Pour les sortir de ces groupes, ajoutez à chacun de ces groupes (onglet-carte, onglet-fond) :
     "except": ["core-checkbox", "core-option", "core-select"]
     Un groupe qui a déjà un "except" le complète, sans en ajouter un second qui remplacerait le premier :
     onglet-texte : "except": ["core-field", "core-checkbox", "core-option", "core-select"]
     Un groupe écrit en liste, ["racine"], devient { "roots": ["racine"], "except": [...] }.
  ```

  Une racine n'entre pas dans cette ligne (un groupe ne peut pas laisser dehors sa propre racine) : une consigne à part dit de l'ajouter à `except` des autres groupes (elle reste dans le sien) ou, quand deux groupes la déclarent racine, de la garder racine d'un seul et, dans chacun des autres, de la retirer de `roots` **et** de l'ajouter à `except` (un groupe qui l'atteint encore par une autre de ses racines ne s'en sortirait pas autrement), ou de réunir les groupes.
- **Un composant du groupe que lit aussi un composant extérieur** reste dans le groupe, et son chemin pointe vers le groupe : toute page qui l'utilise charge le groupe entier. Le build avertit en le nommant, pour que vous le sortiez du groupe ou assumiez ce chargement. Une racine appelée depuis l'extérieur est l'usage prévu, sans avertissement.
- **Un descendant atteint à la fois par un composant exclu et par un composant du groupe reste dans le groupe** : seul ce que l'exclu atteint seul sort avec lui. Si cet exclu appelle un tel composant, une page qui n'utilise que l'exclu charge le groupe par ce composant, et le build l'avertit en le nommant (l'exclu y figure parmi les appelants extérieurs).
- **L'avertissement « utilisé hors du groupe » propose la solution** : ajoutez le composant à `except` du groupe pour le laisser en fichier séparé. Un composant de `except` ne le déclenche jamais.
- **Un fichier de page l'emporte pour sa route.** Quand une route prérendue demande `render.startup: "bundle"`, son fichier de page assemble les composants de la page, y compris ceux d'un groupe ; la fiche de la route désigne ce fichier. Le groupe sert partout ailleurs.
- **Une racine inconnue, un module comme racine, un groupe vide, un nom de groupe invalide** sont refusés à la lecture de la configuration ou au build, avec le nom fautif ; de même, dans `except`, un nom qui n'est pas un composant du projet (un module compris), une racine du groupe (elle ne peut pas être laissée dehors), une clé inconnue de l'objet, ou une valeur qui n'est pas une liste de noms.
- Avec `js: "bundle"`, rien n'est regroupé : le fichier unique livre déjà tout le projet.

Pour charger un groupe d'avance, au survol d'un onglet par exemple, voir `µ.Autoloader.preload` dans [21 · Navigation](21-navigation.md).

### `render.renderQueue`

Plafond de **concurrence** sur le rendu SSR par requête (`mjs dev`/`mjs serve`, bloc `render` — cf. [19 · SSR](19-ssr.md) pour `render.engine`/`render.browserPool`, les autres réglages du moteur de rendu) : `concurrency` (entier ≥ 1, défaut **4**) borne le nombre de rendus EN MÊME TEMPS, `maxQueue` (entier ≥ 0, défaut **32**) le nombre de requêtes qui patientent derrière avant refus. Sans ce plafond, une route paramétrée (`/produit/:id`) ouvre un espace d'URLs quasi infini, chacune un rendu complet lancé sans limite.

```json
{
  "render": { "renderQueue": { "concurrency": 8, "maxQueue": 64 } }
}
```

Au-delà de `concurrency` + `maxQueue` requêtes simultanées, le serveur répond `503 Service Unavailable` plutôt que de laisser la file grossir sans borne ou de saturer le process — `mjs dev` et `mjs serve` posent tous deux l'en-tête `Retry-After` (secondes avant nouvel essai) sur ce `503`.

### `render.stream`

Sert les pages HTML **en flux** (`mjs serve`, `mjs dev`) : le statut, les en-têtes et la coquille de la page (`<head>`, feuilles) partent dès la requête, avant le chargeur de données (`serve.server.mjs`) et le rendu ; le reste de la page suit quand il est prêt. La page reçue est octet pour octet celle d'un bloc. Défaut `false` ; surchargeable par route, la route gardant le dernier mot :

```json
{
  "render": {
    "stream": true,
    "routes": {
      "/":            { "component": "mjs-landing", "stream": false },
      "/produit/:id": { "component": "mjs-produit", "mode": "ssr" }
    }
  }
}
```

Le statut part avec la coquille : un rendu qui échoue ensuite garde le `200` déjà envoyé, la page d'erreur suit avec les mêmes octets que d'un bloc — détail et arbitrages : [19 · SSR](19-ssr.md#page-servie-en-flux--stream).

### `render.startup`

Ce que le HTML figé d'une page prérendue dit au navigateur de charger, **avant** que le manifeste (`bundle_modular.js`) n'ait été téléchargé puis exécuté. Le manifeste est le seul à savoir quels composants une page affiche : sans cette clé, ils ne partent qu'après lui, en seconde vague. La page prérendue, elle, le sait dès sa construction — c'est ce que cette clé exploite. Surchargeable par route (`render.routes["/"].startup`) ; ne concerne que les routes `prerender`.

| Valeur | Ce que le navigateur charge |
|---|---|
| `preload` (défaut) | le fragment porte un `<link rel="modulepreload">` par unité de son **ensemble de démarrage** — composants ET modules — en tête du fichier. Un fichier par composant, `µ.paths` intact : seule la date de départ change (première vague au lieu de la seconde) |
| `bundle` | en **plus**, un `mjs_page-<page>-<empreinte>.js` par page assemble ses composants : le fragment porte un lien vers ce fichier, un lien par module, et une fiche JSON que le manifeste relit pour y repointer `µ.paths`. Une requête de composants au lieu de N |
| `none` | aucun en-tête : la balise du composant racine et son HTML prérendu, rien devant |

Avec `js: "bundle"`, le fragment reste nu quelle que soit cette clé : le fichier unique livre déjà le cœur et tous les composants, il n'y a rien à précharger page par page. Le build le signale en une ligne.

L'**ensemble de démarrage** d'une page, ce sont les composants dont la balise est dans son HTML prérendu, plus la fermeture de leurs dépendances directes : un enfant qu'un `{if}` faux n'a pas rendu en fait partie (il s'affichera au premier clic sans aller-retour), les modules `@import`-és par ces composants aussi.

```json
{
  "render": { "default": "prerender", "startup": "bundle", "routes": { "/": { "component": "mjs-landing" } } }
}
```

Le fichier de page n'est assemblé qu'en **construction de production** (`mjs build --prod`) : en développement, `bundle` se comporte comme `preload`, avec une ligne d'information au journal du build — le rechargement à chaud n'est pas mêlé à un second assemblage. Restent **externes** au fichier de page : le cœur, les feuilles partagées, les animations, les fichiers de langue, le manifeste externe, et les **modules** — un module doit rester une instance unique, un store exporté par un module et dupliqué dans un fichier de page casserait l'état partagé. Les fichiers séparés de chaque composant existent toujours : une autre page les charge seuls, le rendu serveur les lit un par un.

Une page de moins de deux composants n'a rien à factoriser : elle reçoit le préchargement seul. `render.startup: "bundle"` avec `js: "bundle"` est refusé à la lecture de la configuration — le fichier unique livre déjà tout le projet, un fichier de page n'aurait rien à assembler.

Le nom du fichier de page vient de l'**URL de la route** : `/` donne `mjs_page-index-<empreinte>.js`, `/a/index` donne `mjs_page-a-index-<empreinte>.js` (tout ce qui n'est ni lettre ni chiffre devient un tiret). Deux routes qui arriveraient au même nom sont refusées à la lecture de la configuration, nommées toutes les deux : une seule garderait son fichier. Avec `render.locales`, les langues d'une même route partagent leur URL, donc leur fichier de page — il assemble l'**union** des composants de toutes les langues, et chaque fragment déclare dans sa fiche l'ensemble de démarrage de SA langue, fermé par les dépendances statiques du gabarit — un enfant déclaré dans une branche `{if}` sur la langue est donc déclaré dans les deux. Un composant qui n'apparaît qu'en anglais est déjà chargé quand la bascule de langue le fait entrer.

La page ne lit la fiche que dans ce `<script type="application/json" id="__mjs_page">`, au premier chargement comme à l'arrivée par un lien interne : un autre élément qui porterait cet id (un contenu de visiteur rendu dans la page, par exemple) est ignoré, et la fiche ne désigne qu'un fichier de page du dossier des fichiers compilés, jamais un fichier rangé ailleurs sur le site.

`csp: true` est compatible : la fiche est un `<script type="application/json">`, de la donnée qu'aucune politique de sécurité n'exécute — rien d'exécutable n'est ajouté au fragment. Les fichiers de page figurent dans `mjs-precache.json` comme le reste des sorties du build, cf. [36 · Application installable](36-application-installable.md).

`mjs serve` sur une route `prerender` dont le fichier figé n'existe pas encore rend la page à la volée : ce HTML-là n'a pas d'en-tête de démarrage — il se comporte comme `none`, les composants partent après le manifeste.

Ce que coûte `bundle` : un composant partagé par plusieurs pages est téléchargé une fois **par** fichier de page qui l'embarque (le cache ne le reconnaît pas d'un fichier à l'autre), et la moindre modification de l'un d'eux change l'empreinte de tout le fichier de page. C'est un arbitrage : une seule requête au démarrage contre une invalidation plus large. Les pages d'entrée, chargées « à froid » par un visiteur qui ne connaît rien du site, sont les premières à y gagner.

### `logLevel`

Le niveau de la console — **côté navigateur** (`µ.log`/`µ.warn`/`µ.error`) et **côté build** (ce que le minifieur retire du bundle, et les avertissements de construction du terminal, pas les lignes écrites à la lecture de la configuration ou à la compilation d'un composant) — réglé par la MÊME clé, du plus bavard au plus muet :

| Niveau | Montre |
|---|---|
| `'log'` | tout — traces, avertissements, erreurs |
| `'warn'` | avertissements et erreurs |
| `'error'` | erreurs seules |
| `'silent'` | rien |

Une chaîne (`"logLevel": "warn"`) pose le MÊME niveau dans les deux environnements. Un objet `{ dev?, prod? }` pose un niveau par environnement — chaque sous-clé absente retombe sur le défaut de SON environnement :

```json
{ "logLevel": { "dev": "log", "prod": "error" } }
```

Défauts : `dev` → `'log'` (tout, pendant qu'on développe), `prod` → `'error'` (les erreurs seules : les avertissements du framework ne s'écrivent plus ; dans un build minifié, ils sortent aussi du fichier construit, sauf ceux des modules cœur). Le niveau de PRODUCTION gouverne aussi ce que le minifieur retire du bundle de production (un build de développement minifié n'en retire rien, un build de production non minifié non plus) : au-dessus de `'log'`, les traces du framework (`µ.log`) ne sont pas envoyées, ni l'appel ni le texte qu'il aurait écrit ; aux niveaux `'error'` et `'silent'`, ses avertissements (`µ.warn`) non plus ; au niveau `'silent'`, ses erreurs (`µ.error`) non plus, sauf quand le journal des erreurs est embarqué. À ces trois niveaux, les messages du framework qui ne servent qu'au développement ne sont pas envoyés non plus, ni l'appel ni son texte : un conseil d'écriture, une mauvaise utilisation que la construction de développement signale déjà (une option inconnue de `µevery`, une clé inconnue de `:viewTransition`, un verbe inconnu dans `mjs-method`…), un message que seule une construction de développement peut écrire. Un message qui peut venir des données, du réseau, du serveur ou du navigateur du visiteur reste ; une construction de développement les écrit tous, et `'log'` les garde en production. Les modules cœur (`<@@number>`, `<@@select>`…) gardent leurs avertissements et leurs erreurs, avec leurs textes : le niveau les rend muets à l'exécution, sans les retirer. Pour garder les avertissements en production, sauf ceux du développement seul : `{ "logLevel": { "prod": "warn" } }`. Le terminal de `mjs build`, `mjs dev` et `mjs check` suit le niveau de l'environnement du build — la production avec `--prod`, le développement sans : ses avertissements de construction s'écrivent, sauf quand la clé fixe ce niveau à `'error'` ou `'silent'`. Les lignes écrites à la lecture de la configuration ou à la compilation d'un composant (`[lint.config]`, `[lint.a11y]`…) ne lisent pas ce niveau : seul le bloc `lint` les coupe. Détail complet, et l'échappatoire `µ.debug` : [34 · Déboguer](34-deboguer.md).

## 3. Validation stricte

Comme pour chaque bloc imbriqué (`ws`, `ws.limits`, `render`, `lint`…), la validation de `mjs.config.json` est **stricte** : une clé absente de la liste ci-dessus fait échouer le build, avec un message qui nomme la clé fautive et rappelle la liste complète des clés valides. Une faute de frappe n'est donc jamais absorbée en silence.

Le fichier entier doit être un objet (`{ … }`) : un tableau ou `null` est refusé. Les valeurs aussi sont vérifiées à la lecture : `varPrefix` et `defaultTheme` sont des chaînes (un tableau `["dark"]` est refusé), une langue de `render.locales` ne sort pas du dossier du prérendu (segment `..`, barre inverse, chemin absolu), et `manifestPath`, `dev.host`, `image.widths` suivent les règles du tableau ci-dessus.

## 4. Tests du framework : ne jouer que ceux d'un changement

> Cette section concerne le dépôt de ModularJS lui-même, pour qui y contribue : elle ne parle pas d'une application construite avec MJS.

La suite du framework compte près de 2 800 fichiers de test ; une liste de 160 d'entre eux dure déjà 40 minutes. `npm run test:lies` ne joue que les tests liés à vos changements, dans un budget de 5 minutes :

```bash
npm run test:lies                                        # les fichiers que git voit modifiés, ajoutés ou supprimés
npm run test:lies -- src/runtime/mjs_for.ts              # ou les fichiers que vous nommez
npm run test:lies -- --a-blanc src/mjs-ws/streams.ts     # le choix et le plan, sans rien jouer
```

**Le choix.** Un test est lié à un fichier changé quand :

- il l'a **lu** pendant un passage précédent. C'est le *relevé* : le crochet commun des tests (`tests/helpers/tmp-sweep.ts`, chargé par `npm test`) note, pour chaque fichier de test, les fichiers du dépôt qu'il lit (le runtime, les modules du cœur et les images que le Bundler lit en fichier, les sources qu'un test relit, ses fixtures), sa durée et ses rouges, dans `node_modules/.cache/mjs-tests/` ;
- il l'**importe**, lui ou l'une de ses aides de `tests/helpers/` (lien direct), ou par une chaîne d'imports dans `src/` (lien à distance) ; le graphe des imports est recalculé à chaque appel ;
- c'est le test changé lui-même.

Pour un fichier du cœur (`src/core-modules/`), d'un effet ou du runtime (`src/runtime/`), les tests qui le **visent** passent devant : ceux dont le nom le désigne (`core-select-…` pour `select.mjs`, `for-…` pour `mjs_for.ts`), puis ceux dont la source le cite (le nom du fichier, un import, la balise `<@@select>`, l'effet `*liquid` pour `mjs_fx_liquid.ts`). Le constructeur du Bundler lit tous les modules du cœur : presque tout test relevé « lit » `select.mjs`, et les tests du module passeraient sinon après une centaine d'autres.

Les tests **sans relevé** sont choisis aussi, et signalés : chaque passage de `npm test` ou de `npm run test:lies` complète le relevé.

**Le budget.** Les choisis passent par priorité (test changé, nommé, cité, lien direct, lien à distance, sans relevé), puis famille par famille (le début du nom du fichier : `core-select`, `await`, `i18n`…), du plus court au plus long, chaque famille gardant un représentant avant qu'une autre en ait deux. Le budget coupe par la fin de cet ordre : le premier test qui ne tient plus n'est pas joué, ni aucun de ceux qui le suivent, même plus courts ; un test plus long qu'une voie entière est seul mis de côté. Ce qui n'est pas joué — un changement du transpileur touche les deux tiers des tests — est listé « non joué » dans un fichier dont le chemin s'affiche. Les tests se jouent sous `script/test-enclos.sh`, en plusieurs processus mocha en parallèle (4 au plus, selon les processeurs et la mémoire libre) ; le plan remplit 80 % du budget, la passe est coupée à 90 %.

**Un seul navigateur.** L'outil joue Chromium seul (`MJS_MOTEURS=chromium`) ; `MJS_MOTEURS=tous npm run test:lies` joue Chromium, Firefox et WebKit. La variable vaut aussi pour `npm test`, qui joue les trois moteurs quand elle manque : le lancement d'un moteur écarté saute le test ou le crochet qui le demande (compté « pending »), et une ligne en fin de passage dit combien. Un fichier de test qui exige d'autres moteurs le déclare par une ligne ; ses lancements de ces moteurs passent toujours :

```ts
// moteurs exigés : firefox webkit
```

**Un rouge se rejoue seul**, après la passe, par ordre de priorité, avant d'être cru : vert seul, il est dit « instable » ; rouge encore, « rouge ». Faute de temps, il reste « rouge non rejoué », avec le temps qui restait et celui qu'il fallait. Les rejeux partent après la passe principale, coupée à 90 % du budget, et finissent 5 s avant lui : un budget trop court pour en loger un (`--budget 90` laisse 4 s, moins que le démarrage d'un mocha) le dit dès le plan, avec le budget qui en laisse la place. Le code de sortie vaut 1 dès qu'un rouge est confirmé ou qu'un rouge n'a pas pu être rejoué dans le budget. Les journaux de chaque voie et la liste des non-joués restent dans `node_modules/.cache/mjs-tests/passes/` (les 10 derniers passages).

| Option | Effet |
|---|---|
| `--budget <s>` | budget en secondes (300 par défaut) |
| `--voies <n>` | nombre de processus mocha en parallèle |
| `--a-blanc` | montre le choix et le plan, ne joue rien |
| `--build` | reconstruit `dist/` (`npm run build:self`) s'il est plus ancien que `src/`, au lieu d'écarter les tests qui passent par `bin/mjs` |
| `--tout` | tous les tests sont candidats, ceux sans relevé d'abord : pour remplir le relevé par tranches |
| `MJS_TEST_TRACE=<dossier>` | déplace le relevé ; `MJS_TEST_TRACE=0` l'éteint |

Une copie du dépôt dont `node_modules` est un lien vers celui d'un autre arbre n'écrit pas dans le cache de cet arbre : son relevé est éteint tant que `MJS_TEST_TRACE` n'est pas posé.

**Ce que l'outil ne garantit pas.**

- Un vert de `test:lies` n'est pas un vert de la suite complète : les tests non joués faute de budget, et ceux qu'aucun lien ne rattache au changement, ne sont pas joués.
- Le relevé ne voit pas ce que lit un sous-processus (`bin/mjs`, un mocha lancé par un test) ni un worker. Un test qui lance `bin/mjs` est lié à tout `src/` ; il est écarté tant que `dist/` est plus ancien que `src/`, sauf avec `--build`.
- Une lecture mise en cache pour tout le processus n'est rattachée qu'au premier fichier de test qui la provoque. Le relevé fait l'union des passages, ce qui la rattrape avec le temps, et ne retire jamais une lecture qu'un test a cessé de faire : le choix pèche par excès, jamais par défaut.
- Le graphe des imports est statique : un import dont le chemin se calcule n'est pas vu.
- Chromium seul ne voit pas un défaut propre à Firefox ou à WebKit : avant une publication, jouez `MJS_MOTEURS=tous` et la suite complète.
- Les durées du relevé dépendent de la charge de la machine au moment où elles ont été prises.
- Les bancs de `tests/browser-smoke/` (`npm run test:browser`) ne sont pas candidats.
